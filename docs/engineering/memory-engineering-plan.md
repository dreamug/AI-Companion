## 1 决策与交付范围

整体方案采用五层记忆：原始对话、当前对话记忆、长期事实、事件记忆、待跟进事项。SQLite 保存权威记录；上下文、摘要和向量索引根据记录生成，并保留依赖关系。

确定采用以下设计：

1. 已确认事实采用独立、固定的 2000 token 预算，置顶事实计入其中；边界和日摘要另设预算。按完整事实投影大小在 all/hybrid 间分流，并设置 2000/1700 token 滞后区间，避免日摘要长度使模式反复变化。
2. 候选生产、展示、确认和退出的漏斗先于正式迁移评估；聊天内确认交互作为独立阶段。只有事实规模或真实漏召回说明需要，才提高向量接入的实施优先级。本地模型仍选 `intfloat/multilingual-e5-small` 384 维，固定 revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`。
3. 向量存于每个 bot 的 SQLite BLOB 表，常驻向量缓存可丢弃重建。首期精确余弦扫描，不引入独立向量数据库或 SQLite 向量扩展。
4. 补充分段对话摘要，保护即将移出近期窗口的交流。摘要能帮助继续对话，不直接升级成已确认用户事实。
5. 新确认和更正立即进入读取路径，后台生成索引。索引未完成不造成事实暂时不可见。
6. 检索超时或模型未就绪时回退关键词；取消和遗忘属于失效条件，不能作为继续检索的理由。
7. 用真实运行状态驱动临时等待提示。提示不成为聊天消息，不写记忆、不触发语音。

基础交付包括候选统计、聊天内确认、共享读取入口、摘要与依赖失效、来源展示、延迟诊断和完整 Harness 验收。正式迁移在产品门槛复核后推进；本地编码 worker 和混合检索是已选型但按证据推进的增量，不是确认系统尚未工作时的必做前置。保持原有单用户、多 bot、每 bot 单前台 Run 的部署模型。

本阶段不加入自动亲密度、人格自我改写、未经确认的长期画像、所有聊天全文向量化、关系图数据库、多 Agent 记忆整理、自动外发给新服务的 Embedding。用户是否授权提醒，仍由跟进领域决定，不能由记忆相关度推导。

## 3 领域对象和信任边界

### 3.1 五层记忆

| 层           | 主要内容                                             | 权威性与生命周期                               | 模型如何读取                             |
| ------------ | ---------------------------------------------------- | ---------------------------------------------- | ---------------------------------------- |
| 原始记录     | 用户发言、助手生成与展示事实、人工确认和工具成功回执 | 来源证据；保留到明确删除或保留策略执行         | 近期原文，或通过受限读取展开来源         |
| 当前对话记忆 | 当前主题、选项、指代、已作决定、未解决问题           | 有来源的派生摘要，不是个人画像；按交流范围失效 | 近期原文加最新有效分段摘要               |
| 长期事实     | 用户确认的身份、偏好、称呼、长期约定                 | 来源、主体、有效期明确；可更正和撤销           | 预算内全量，否则混合检索                 |
| 事件记忆     | 一次已发生交流或用户报告的事件、日期、参与者、结果   | 事件发生时间与得知时间分开；不把计划改写成结果 | 近期日摘要、时间／主题查询和按需来源展开 |
| 跟进事项     | 待办、开放问题、已确认提醒、完成状态                 | 沿用 FollowUp/Series/Delivery；有独立执行权限  | 最多若干条相关且有效的已确认事项         |

人格和安全规则属于配置，不属于可由记忆提取修改的对象。动态工作状态属于当前状态，不靠检索猜测。向量、检索排序、摘要措辞没有执行权限。

### 3.2 来源必须表达说话者与现实范围

目标补充 `realityScope: reality | roleplay | unspecified`，以及 `subject`、`speaker`、`occurredAt`、`learnedAt`。现实和虚构是数据维度；不能只在提取提示词里区分。

- 用户说“我养猫”，可以成为用户陈述候选；确认后成为长期事实。
- 助手说“你可能喜欢猫”，只能记录为助手猜测，不能成为用户偏好。
- 用户与角色编写的虚构旅行，可保留为 roleplay 事件，不进入现实履历。
- 用户说“下周去青岛”，保存为计划或跟进；日期到达不证明已经出发。
- 工具成功回执证明该工具实际完成的行为；助手的口头承诺不替代回执。

当前 `persona.memoryScope` 只影响提取提示词，不证明历史记录已具有可靠范围标注。迁移不能根据当前人格把全部旧事实重新解释为现实或虚构。可由原始来源明确判定的按来源标注，其余为 unspecified；展示时保留不确定性，不参与跨范围自动推断。每个事实的来源不可为空，避免 `every([])` 被当成有效证据。

旧有已确认事实不因缺少新字段被自动删除或撤销确认。unspecified 的具体读取资格见 7.1；不会把“附带标签纳入”与“因查询范围排除”留给各实现自行选择。明确范围由服务端人格与来源规则解析，模型不能通过查询参数将虚构事实声明成现实事实。

### 3.3 事实状态与确认

```text
用户来源 → pending 候选 → 明确确认 → active/confirmed
                         → 暂缓 → pending，延长待处理期限
                         → 丢弃 → deleted
active/confirmed → 明确更正 → 旧记录 superseded，新记录 active/confirmed
active/confirmed → 发生冲突但对象不清 → 新候选 pending/disputed
任何内容 → 遗忘 → deleted，并清理其派生内容
```

普通自动提取仍需确认。保留“7 天、20 条”作为兼容起点；超量或到期退出待处理列表，原文仍可查，不升级为事实。重复合并以作用域、主体、主题、时间和来源为依据，不能只按相似度覆盖。

第一版保留维护页，并增加聊天内候选卡片，确认、更正和删除仍进入同一命令入口。用户自然语言要求“记住”时，立即提供与目标候选绑定的可确认操作；尚未成功写入不得说“已经记住”。不增加未经验证的自动确认能力。机制、展示频率和指标见 6.4–6.5，不能以一句“自然提示”替代实现。

用户当前明确纠正的内容立即影响本轮回答；长期写入是否已完成另行表达。称呼禁用、停止、遗忘和免打扰继续走即时领域命令。歧义目标先澄清，不能由模型自行选一条破坏性修改。

## 4 身份与状态生命周期

| 身份       | 拥有的状态                             | 结束时行为                                  |
| ---------- | -------------------------------------- | ------------------------------------------- |
| 应用进程   | 一个 E5 模型 worker、模型版本描述      | 停止任务并关闭 worker，不保留无归属正文日志 |
| bot 关系   | 数据库、记忆版本、向量缓存、段落与摘要 | 归档停止任务并清缓存；恢复从库重建          |
| 内部交流段 | 开始结束顺序、摘要块、覆盖范围         | 封存后仍可回查，不清事实、不清历史          |
| Run        | 输入顺序、取消信号、投影、检索诊断     | 完成或取消即终结，不由缓存重新启动          |
| 后台 Job   | 固定输入修订、策略版本、epoch、进度    | 幂等完成，过期快照丢弃，必要时重新捕获      |
| 工具调用   | runId、callId、参数指纹、结果          | 同调用幂等；不同参数冲突，不重放副作用      |

所有请求与返回绑定 `ownerUserId + relationshipId`；数据库路径是 bot 的物理隔离，不能替代字段校验。worker 共享模型权重，不共享未隔离的查询缓存。首版不做查询结果缓存，减少更正和遗忘的失效面。

Run 的历史沿用接受顺序 `enqueueSeq`。事实或摘要引用的消息若来自更晚排队输入，不得进入较早 Run；人工确认等管理命令可在投影时生效。检索等待期间发生更正、来源变化或 epoch 变化，应重新核验依赖；明确边界变化沿用当前取消机制。不能仅检查“编码开始时没删”就接受返回。

## 5 内部交流分段和对话摘要

### 5.1 自动建立交流段

继续使用固定用户可见 thread；新增内部 `conversation_segments`。

- bot 第一次接受输入时，在同一输入事务中建立 segment 并绑定 Run。
- 与上一条用户输入间隔超过 30 分钟、且旧段没有 queued/running Run 时，新建 segment。30 分钟为可调初始参数。
- 有排队或运行任务时保持同段；用户主动换话题只更新对话内容，首版不额外调用模型做话题分类。
- 结束旧段不触发事实删除，不强制清空上下文；允许带上最近一个相关交接摘要。
- 重启恢复 segment 元数据，不自动重跑用户聊天。旧库按输入顺序分批回填段归属，不在首个前台请求里扫描并摘要全部历史。

分段用于组织来源与摘要；更长时间的关系连续性由事实和事件负责。不能将“新段”解释成“以前没有聊过”。

### 5.2 摘要策略

首版采用“原始交流分块摘要随窗口滚动”，不无限累积摘要的摘要。

1. 按 Run 组成用户输入与已展示助手输出的完整交流组；分条助手回复属于同一组。未显示的尾段不进入摘要。
2. 近期原文达到历史预算的 75%，或达到 18 条消息时，后台准备即将移出的最旧完整交流组。两者是软触发参数，最终以预算为准。
3. 每个摘要 Job 最多包含约 4000 输入 token 的原文块，保持交流组边界；单组超限则保留带明确位置的片段并登记未覆盖范围，不能声称完整覆盖。
4. 输出至多约 1000 token；结构包含主题、已讨论选项、用户明确决定、仍开放问题、关键实体和来源引用。程序检查引用存在、说话者、输入范围、输出长度及字段，不把模型的语义正确性当成已由 Schema 保证。
5. 每个块直接基于原文，不拿上一个摘要替代全部原文。默认选择最新相邻有效块进入至多 1500 token 的当前对话摘要预算，最多 2 块；更早块通过 7.2 的 conversation 检索后端找回，不能只保留在数据库而无读取入口。
6. 摘要与覆盖游标同事务提交。覆盖范围只推进到成功归纳的稳定交流边界，失败不提前推进。

摘要出现的信息按原文身份表达：“用户说”“助手建议”“用户尚未选定”。丢失问句、否定、数量、选项对应关系和未决事项均属于保留质量失败。用户未确认偏好可以作为“刚才说过的内容”帮助续聊，但不能据此创建 confirmed 事实。

### 5.3 展示回执与来源

现有 Source 主要对应用户输入和人工来源。新增 `EvidenceRef` 支持引用当前 Source、消息及其已展示前缀、记忆修订和摘要；不伪造用户来源来装助手内容。

```ts
type EvidenceRef = {
  entityType: "source" | "message" | "memory" | "summary";
  id: string;
  revision: number;
  startUtf16: number;
  endUtf16: number; // UTF-16 半开区间，可直接对应 JS slice
  visibleEndUtf16?: number; // 消息采用捕获时已确认展示的末端
  sliceHash: string; // 精确区间原文的 SHA-256，不是整条消息 hash
};
```

所有文本偏移和展示回执统一为 UTF-16 code unit。端点落在 surrogate pair 中间就拒绝该偏移，由调用方重算合法边界，不得向外扩过 displayed；来自 Python tokenizer 的偏移显式换算后再持久化。输入 "A😀𠮷B" 的合法边界为 0、1、3、5、6，测试包含组合字符和换行。

sliceHash 只 hash `text.slice(startUtf16, endUtf16)` 的原始 UTF-8 编码，不做 NFKC 或空白归一化。助手证据还要求 endUtf16 不超过捕获时与当前已展示末端。展示回执只增长时，旧切片和 hash 不变，不使摘要失效。只有 message 的追加／展示变化允许在版本不同时重查同一区间、删除和显式撤销后继续；source、memory、summary 的业务修订仍严格匹配，不能用相同文字绕过主体／范围更正。整条内容 hash 若用于传输诊断，另名 contentHash，不替代切片有效性。

对历史助手消息没有可靠展示证据时，不回填“用户肯定看过”。保守保留用户发言及缺口标记。

### 5.4 摘要失败与硬裁剪

新消息优先，摘要不阻塞前台等待远程调用。达到硬预算而摘要尚未完成时，使用已有有效摘要并保留尽可能多的最新完整交流；其余记录 `history_budget` 和 `summary_pending/failed` 缺口。必要时受限展开原始来源，不能编造缺失细节。

该退路意味着极端长聊或摘要服务故障时不承诺全部早期细节仍在上下文。验收要报告缺口率，而不能只测“没有超限”。跨日仍执行兼容日摘要任务；它与当前对话摘要不相互替代。

## 6 长期事实与事件写入

### 6.1 用户输入后的工作

用户输入、Source、Run、segment 归属及提取工作标记在同一短事务内持久化。现有成功回复后才排提取可能漏掉中断 Run 的用户事实，目标改为：输入时登记资格，前台结束后空闲处理；未完成助手输出不成为提取依据。

提取同时提供当前用户输入之前最近一条已展示助手提问作为 `contextOnly`，最多 500 token，绑定消息可见切片；来源截断跨不过当前 Run 的 cutoff。例如“你周末一般干嘛？”→“爬山”，允许生成“用户说周末一般爬山”的候选，事实来源仍是用户回答。助手语境只能解释省略，不能提供用户没有承认的属性：“你是不是医生？”→“不是”不能提取成医生。撤销或更正这段语境时，相应提取依赖也失效；不提供未展示内容或后来助手回复作语境。

任务键为 `extract:{scope}:{sourceId}:{sourceRevision}:{strategyVersion}`。来源已变更、被撤销、开关关闭或超出记忆范围时不处理；运行前检查一次，提交前再检查。重启扫描有提取资格但无终态进度的来源，补工作而不补跑聊天。

提取结果先去重，再创建 pending 断言和未确认 open_loop；结果、来源依赖与提取进度同事务提交。自动提取保持最多 8 条断言、5 条事项的当前起点。失败有限重试：暂时网络错误最多 2 次，间隔 5/30 秒；Schema、来源错误不自动重试。前台抢占不计入内容失败次数，任务退回 pending。

### 6.2 确认和冲突

确认命令带 expectedRevision，事务内再查状态与来源，并写确认来源、记忆变化版本、索引工作标记。明确主题冲突不能仅因 `topic` 相同就覆盖：至少比较主体、现实范围、时间、谓词和限定条件。

“以前喝咖啡，现在喝茶”可结束旧事实有效期并建立新修订；“喜欢茶，也喜欢咖啡”是并存；“这个周末不喝咖啡”是限时条件。无法判定进入 disputed 候选，保留现有已确认事实且避免断言冲突结论。

### 6.3 日摘要与事件

`Memory.kind=episode` 继续使用，新增 `episodeType: daily | shared | reported`。

- 旧有 day 记录映射为 daily，内容仍标注 derived，不自动改成用户 confirmed 事实。
- shared 表达可证实的双方交流事件，例如“讨论过两个方案，用户选择了第二个”；只使用实际展示的助手内容和用户来源。
- reported 表达用户报告的外部事件，明确“用户说”，不声称助手现实在场。

日摘要保留最近一个有消息已结束日、无消息不生成、删除后禁自动重建的兼容规则。目标按原文预算和完整交流组选取，记录 `coverageStart/End`、实际 EvidenceRef 和 `partial`，不能只截最后 60 条却声称覆盖全天。

事件自动归纳可以产生带来源的派生候选，作为历史回忆数据；涉及用户现实履历的新断言仍需确认。事件的 `occurredAt` 与 `learnedAt` 分开；来源没有明确日期时标未知或范围，不拿生成时间冒充发生时间。

首期 E5 索引只覆盖合格的已确认长期事实。事件按日期、主体、主题和关键词读取；事件语义索引作为独立后续开关，需新增专门评测，不能直接套事实实验的准确率。

### 6.4 聊天内确认是独立交付

候选卡片有“记住”“更正后记住”“稍后”“不保存”四种操作，绑定 candidateId、expectedRevision 和源片段。卡片是管理控件，不作为角色消息、助手经历或 TTS 输入。原有维护页继续可用；两个入口共享幂等确认命令，重复点击不产生多份确认来源。

用户明确请求保存时，当前目标卡片可立即显示，不占系统主动提示配额。其他候选只在新的用户输入与候选 topic／关键词有直接交集，且来源有效、未过期、非 interpretation、无 disputed 冲突时排入展示候选；不额外请求模型判断“适不适合提示”。同一 bot 同时最多一张待处理卡片，每个用户自然日最多主动展示一张，同候选不重复主动展示。

危机路由、专注、免打扰、正在发送分条回复、无关话题和离线状态不主动显示。错过机会不补通知；下次相关输入可以再判定，明确“不保存”立即退出。展示文本为待确认的简短原文及可展开来源，不默认勾选，不把关闭卡片或没有回复当同意。

点击“记住”复查来源、修订、有效期与冲突；成功回执后卡片显示已保存，新事实进入下一轮。更正走相同事实修订命令；暂缓只延长候选处理期限；丢弃不自动删除用户原始发言。聊天中单独回复“对”暂不作为全局确认命令，以免确认错对象。

当前 discard 实现复用了 forget，会推进 epoch。MEM-C 要区分“pending 不保存”与明确遗忘：前者只结束该候选、记录退出原因，清其派生内容，不修改其他事实或中断无关 Run；后者继续完整删除台账流程。不得直接沿用旧入口的副作用而违反 10.3 的版本合同。

### 6.5 候选漏斗和产品门槛

先在现有 Memory JSON 增加可选 lifecycleMetadata，不依赖 v2 新表：origin（automatic/manual，不被 manual 字段变化覆盖）、trafficOrigin（natural/synthetic/unknown，来自服务端运行环境）、proposedAt、firstOfferedAt、decidedAt、terminalReason（confirmed/discarded/expired/overflow/replaced/source_invalidated）。所有状态转移与事实同事务记录，不依赖会被截断或清空的公开事件重建历史。旧记录未知字段保持 unknown，不倒推。

只聚合元数据，报告按 bot、自然日和创建 cohort 统计的生产量／每百条输入生产量、待处理年龄、展示机会数、实际展示率、展示后确认率、成熟 cohort 确认率、过期率、超量退出率、修正与丢弃率。实际展示需客户端回执，但不声称已经阅读。按候选 ID 去重，明确每个分子分母与观察窗；尚未满 7 天的 cohort 不当作“未确认失败”，遗忘或缺失样本按 censored 另报。遗忘清除可关联的 lifecycle 元数据，不以观测为由保留用户内容或身份副本。

MEM-G0 先输出只读快照与可识别性报告；当前快照已做，但确认率／过期率尚不可识别。接入 lifecycle 与聊天卡片后，MEM-G1 至少观察 7 个自然使用日，排除 synthetic/unknown；不足 10 个实际展示的自动候选时只报计数和“样本不足”，不把比例当稳定结论。低候选量本身支持先保持 all，不为凑样本强行多提取或打扰。

MEM-2 开始前必须有 MEM-G1 评估记录及明确的阶段取舍。若确认前大量流失，先迭代 MEM-C；若已确认事实持续放得下，MEM-4 降为后续增量。只有固定事实预算被真实事实持续超过、或受控重现的真实问法漏召回影响使用，且确认入口基本可用时，才推进向量服务。样本不足不等于门槛自动通过，不以合成检索高分替代自然漏斗。

## 7 读取与检索合同

### 7.1 统一资格

`eligibleFacts(scope, now, cutoff)` 为全量、关键词、向量和最新事实旁路提供同一规则：当前作用域、assertion、active、confirmed、非 disputed、非 interpretation 推测、来源非空且修订有效、当前有效期内、未过 expiresAt，且来源没有越过 Run 的输入顺序。现实范围按下表执行，不作为含糊的自由判断：

| 服务端解析的读取域               | reality                  | roleplay | unspecified                                    |
| -------------------------------- | ------------------------ | -------- | ---------------------------------------------- |
| 普通现实／个人偏好查询           | 纳入                     | 排除     | 纳入原文并附未标范围标签；不据此断言线下事件   |
| 明确限定真实履历或线下已发生事件 | 纳入有匹配事件依据的内容 | 排除     | 排除出肯定证据，可提示旧记录范围未确认         |
| 明确虚构／角色扮演查询           | 仅用户明确带入的背景     | 纳入     | 可作未标范围的旧记录呈现，不补成虚构或现实事实 |

旧记录缺字段映射 unspecified，因此普通老用户查询不会突然失去全部既有确认事实。读域由当前用户要求与已发布配置确定，冲突时澄清，工具不能伪造用户选择。资格纳入不等于足以回答属性；主体或时间仍不清楚时不能肯定回答。

episode、当前摘要和跟进使用各自资格函数，不能因 active 就当 confirmed 事实。资料指令一律作为引用数据，不能覆盖人格、工具权限或当前明确边界。

资格扫描按稳定 ID 分页读取、累计完整投影预算。超过预算即可停止“全量是否放得下”的试算，进入检索路径；只有扫描到末尾并全部校验才能声称完整读取。不能使用 `list(..., 500)` 的界面分页上限代表全部事实，也不每轮无界反序列化所有历史记录。

### 7.2 统一异步入口

以下为目标合同草案，类型归属项目，不依赖 Embedding 或聊天 SDK 对象：

```ts
interface MemoryReadRequest {
  scope: Scope;
  runId: string;
  cutoffSeq: number;
  now: number;
  query: string;
  recentAnchors: { text: string; evidence: EvidenceRef[] }[];
  target: "facts" | "episodes" | "conversation";
  budgetTokens: number;
  deadlineAt: number;
  signal: AbortSignal;
}

interface MemoryReadResult {
  routeState: "all" | "hybrid";
  mode: "all" | "hybrid" | "keyword" | "structured" | "budget_limited";
  items: MemoryExcerpt[]; // 含当前修订、范围、文本位置和 EvidenceRef
  allEligibleFactsIncluded: boolean;
  state: "ok" | "degraded";
  reasons: string[];
  epoch: number;
  memoryVersion: number;
  contextVersion: number;
  indexVersion: number;
  indexCoverage: { ready: number; eligible: number };
  excluded: { id: string; reason: string }[];
  timing: {
    queueMs: number;
    encodeMs: number;
    scanMs: number;
    totalMs: number;
  };
}
```

`allEligibleFactsIncluded` 只描述本次范围内的已确认事实，不表示已读取所有聊天、摘要或事件。不存在全局“模型知道一切”的布尔状态。检索资格和预算裁剪都可能使结果不完整，分别记录。

将 `buildContext` 拆为准备快照、异步读取、最终纯投影。前台首次请求与 `search_memory` 使用同一个 MemoryRetrievalPort。工具继续受 Run 的请求数、工具数和总耗时限制，不绕过资格、预算与取消。

`executeTool` 的读路径改为异步：验证参数和捕获版本 → 事务外检索 → 核验当前 Run、来源与版本 → 短事务保存工具结果。写工具继续使用现有受控领域命令。禁止把 async 回调直接传给 better-sqlite3 的同步事务。

每个 target 的首期后端明确如下，FTS 均先按作用域、有效来源、cutoff 和范围筛选，失效记录不占最终名额：

| target       | 存储和检索后端                                                                                                              | 找回范围与排序                                                                                    | 是否使用 E5            |
| ------------ | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------- |
| facts        | memories assertion；预算内全量，否则 memory_fts＋精确字面／短词回退                                                         | 本作用域合格事实；字面级别后按 RRF，详见 7.4                                                      | MEM-4 开启且已就绪才用 |
| episodes     | memories episode；日期／主体／episodeType 结构化条件，再查 memory_fts                                                       | 跨所有日期的有效 daily/shared/reported，关键词相关度后按时间和 ID 稳定排序                        | 首期不用               |
| conversation | conversation_summaries＋新增 conversation_summary_fts；segment／原始消息 ID／顺序范围结构化入口，及 topic、entity、正文 FTS | 跨当前和已封存 segment，覆盖所有有效摘要块；明确范围先定位，否则关键词相关度、范围新近度、ID 排序 | 首期不用               |

conversation_summary_fts 与摘要事务一起更新，是可重建派生索引；删除／更正同步删除有关行。中文短词沿用限定范围的 LIKE 回退；FTS trigram 候选池起点 80，范围过滤不通过时有界分页补取。两个历史 target 普通检索最多 5 个片段，枚举走游标；结果带源消息 ID 和可展开区间，不返回仅有“某天聊过”的空标签。

最新两块只决定默认注入，不是历史可读上限。当前输入带明确“之前／那次／上回”等历史指代并有主题／实体线索，或给出日期／源位置时，准备阶段同时执行 facts 与相应历史 target；历史候选替换当前摘要预算中的低相关块，仍最多 2 块、1500 token，不额外堆一份预算。需要更多内容由 search_memory/read_memory_source 有界展开；聊天模型也可主动指定历史 target。

必须用 200 条消息的场景验证：第 30 条附近“海棠项目选 B、A 成本超标”，后续换题并使其退出最新两块，再问“海棠项目当时为什么没选 A”，从旧摘要 FTS 找回并展开支持来源。另测跨 segment 日期查询、同主题相反决定、遗忘旧块后不可找回。没有实体、时间或可解析指代的“上次那个呢”不保证词法命中，应澄清，不能把后端存在等同于已解决任意语义回忆。

### 7.3 全量路径

F 表示本作用域按当前人格默认兼容读域计算的全部有效确认事实投影，含 ID、来源、时间和置顶事实，去重一次；不含日摘要、当前时间、包装、边界或本轮 query。日摘要每天变化不参与模式判断。使用相同排序和序列化策略版本，避免字段排列和动态时间带来数值波动。本轮主体、日期或严格现实筛选不改变 F；若结构化筛选的子集可完整返回，mode 可为 structured，routeState 保持，避免查询类型本身切换全局模式。

| 已保存 routeState | 条件     | 新 routeState |
| ----------------- | -------- | ------------- |
| 无状态（初次）    | F ≤ 2000 | all           |
| 无状态（初次）    | F > 2000 | hybrid        |
| all               | F > 2000 | hybrid        |
| all               | F ≤ 2000 | all           |
| hybrid            | F ≤ 1700 | all           |
| hybrid            | F > 1700 | hybrid        |

routeState 按 scope 与资格／预算策略版本持久化；重启保留。只由完整事实集合或策略变化刷新，旧排队 Run 的 cutoff 子集不反向改全局状态。首次默认从 all 起步，混合索引就绪与否不改变 routeState，失败只影响实际 mode 和 degraded 原因。固定事实预算达到 1500 token 时后台预热和建索引，不要求前台每轮启动模型。

MEM-1 尚未创建 v2 表时，routeState/routingPolicyVersion 用 Settings 的可选 memoryReadState JSON 字段保存，由记忆服务在事实集合变化时短事务更新；MEM-2 再迁入 memory_state。纯投影函数不写路由状态，不为了滞后机制提前做正式 Schema 迁移。预热参数只在 MEM-4 已部署且产品门槛允许时生效，提前阶段不暗中安装或启动模型。

routeState=all 且事实及必选块能放入本轮实际预算时，返回全部合格事实，不编码。总体裁剪后放不下全部事实，则 mode=budget_limited、allEligibleFactsIncluded=false，保留 routeState，不因某一次工具结果变大来回切换。不能悄悄删事实仍称完整读取。

本版有意调整研究方案的“边界＋摘要＋事实共用 2000”：改为事实固定 2000、边界最多 1600、日摘要最多 500，记忆相关总上限 4100；同时降低近期原文和工具交换上限。这个分区取舍是新增工程决定，需重跑总预算和模型输入成本测试，不能直接沿用旧合并预算的质量结论。

不强制预热仅有少量事实的角色。全量读取可能增加回答模型输入，因此上线比较要包含模型首段可见时间和费用，不能只比较本地检索速度。

### 7.4 混合路径

事实使用自己的固定预算，置顶在事实块内优先；关键词与向量候选同时准备。关键词沿用 Store.search 的基础算法但增加统一资格过滤，精确命中保留按下述硬排序规则验收。

实验初始配置固定如下，后续变更需独立验证集：

| 项目         | 初始值                                                          |
| ------------ | --------------------------------------------------------------- |
| 语义候选     | 当前合格向量前 12                                               |
| 关键词候选   | 前 5                                                            |
| 融合         | RRF，k=60，语义权重 1，关键词权重 0.35                          |
| 字面命中     | normalized raw query 是候选正文连续子串；符合下述资格及长度规则 |
| 返回         | 通常最多 5 条，再服从剩余 token 预算                            |
| 相似度硬阈值 | 不设全局阈值，不能把分数当答案概率                              |

RRF 按 canonical memory ID 去重，同一事实的多个片段先按最相关片段聚合，不重复占名额。返回原文和必要限定句，不让检索器自行合成为新事实。资格校验在候选阶段和交给模型前各执行一次；过期项消耗名额时有界补取一次，不无限重查。

`literalHit` 使用当前原始 query，做 NFKC、英文小写、首尾去空白、连续空白折叠；不删除否定、日期、标点，不使用 recentAnchors 或问题改写。规范 query 至少 2 个 Unicode 字符，且规范正文包含完整连续 query 才成立。FTS 命中全部词或只有 trigram 重叠都不算 literalHit。已知主体、范围、时间不符先排除；旧未知主体不能被算法声称“已验证相同主体”。

最终排序为 `(literalHit 降序, literalHit 组内原 Store.search 排名升序, 非字面组 RRF 降序, 稳定 ID)`；同组没有对应词法排名置末。0.35 只影响非字面融合组，不能覆盖 literalHit 的硬排序。测试“乌龙茶”连续命中与“乌龙／红茶”分散词命中、全角拉丁字符、否定词、同名不同主体、超过 5 条字面命中，以及旧基线 16 个精确问题，分别报告 top-5 和进入预算后的命中率。该规则保护的是有定义的精确查询，不承诺任何自然语言问题都等同字面命中。

对于“一共有哪些偏好”“列出所有约定”等枚举问题，不使用普通 top-5 宣称完整清单。走结构化分页读取，在总预算内分页；未读完明确说明范围。首版由明确工具 target 和分页参数支持，不额外添加一次默认模型路由调用。

### 7.5 最新事实旁路和指代

索引任务未完成的已确认新增或更正事实构成 delta 集。混合路径同时考虑当前相关 delta，优先精确主题、主体和关键词匹配；无索引 delta 最多取最近 8 条，受记忆预算约束，并标记 coverage 不完整。不能因“旁路”无界放入全部新增内容。

对于当前用户刚确认的目标事实，使用命令回执 ID 或明确来源将其置于本轮读取候选，保证无需向量即可读取；其他大量未索引事实不承诺任意改写都命中。接近预算时提前后台建索引和预热，降低从 all 转 hybrid 的体验落差。

默认查询以当前输入为主；可带最近 2 个完整交流组中的明确实体和主题，总共最多 256 个 UTF-16 code unit 作为 recentAnchors，边界不能切开 surrogate pair。每个线索有来源。明确指代可以展开，存在多个合理对象时澄清；不默认远程问题改写，不拿完整历史拼成 query，不把展开的推测写入事实库。

### 7.6 空结果和失败

- all 且覆盖完整、目标属性无来源：可以说目前没有记录该属性，不能补猜。
- hybrid 或 keyword 空结果：只能说这次没有找到，不能说“你从来没有说过”。
- worker 未就绪、索引缺失、超时：保留有效关键词结果，state=degraded，并把读取不完整的说明提供给回答模型。
- 用户取消、Run 终止、归档、epoch 失效：立即结束等待，不再用回退发起新工作。
- 权威数据库不可读：明确失败，不把存储故障当成“没有记忆”。

回答是否有依据由问题、证据和限定条件决定，模型可自然弃答。产品聊天不展示相似度、内部 ID 或评估 JSON。

## 8 上下文预算与运行中增长

### 8.1 分区和必选项先预留

先计算 `C = min(requestInputBudget, 已核验模型容量 - maxOutputTokens - safetyMargin)`。requestInputBudget 起点 24000，safetyMargin 起点 1024；模型能力未知时不猜窗口。输出预留在容量式中扣除，不把它再次算进输入预算。

先为真实系统串、当前输入、工具 Schema、当前未闭合工具交换和明确边界预留，再分配可选块。必选项已经超过 C 时在请求模型前明确失败，不截用户输入或伪造工具结果。当前字符输入上限不表示任意 12000 字都必然能装进本次 token 预算。

| 块                           | 初始上限                   | 规则                                               |
| ---------------------------- | -------------------------- | -------------------------------------------------- |
| 系统与人格最终串             | 7000 token                 | 包括分条指令，必选，不静默压缩                     |
| 明确边界                     | 1600 token                 | 独立必选块，不与事实争夺 2000                      |
| 已确认事实含置顶             | 2000 token                 | 固定事实分流预算，含全部来源元数据                 |
| 近期日摘要                   | 500 token                  | 可选，与事实分区分开                               |
| 当前／召回对话摘要           | 1500 token、最多 2 块      | 新近和历史查询共用该块                             |
| 近期原文                     | 4000 token、最多 24 条消息 | v1 的 8000 降到 4000；按完整交流组                 |
| 已确认跟进                   | 500 token、最多 6 条       | 先保留相关到期事项                                 |
| 时间、状态与包装             | 512 token                  | 包括 JSON 字段名和消息包装，实际渲染检查           |
| 运行中工具交换及助手续步文本 | 2000 token                 | v1 的 4096 降到 2000；含工具参数、结果和已生成内容 |

这些上限合计 **19612 token**，较 24000 留出 4388；当当前输入不超过 2000、工具 Schema 不超过 1000 时，所有分区同时到上限也只需 22612，余量 1388。这里定义了可直接固定测试的常规场景，而非让每轮必定裁剪。更长输入、更大工具 Schema 或模型更小容量仍按下一节确定规则裁剪。

单次新工具结果首轮生成最多 1000 token 的有来源节选。当前活跃交换不可拆；本身超过工具块上限时登记例外，并占用剩余可选预算，只有必选总量仍不超过 C 才继续。原文保留在来源库，通过受限读取展开。粗估与提供方实际 usage 分别记录，不能把 tokenEstimate 当准确 tokenizer。

### 8.2 确定的裁剪算法

先用实际完整序列化计算缺口 D。D ≤ 0 不裁剪。否则依次完成下列一个台阶，每个台阶重新渲染计数，首次满足即停止；低于台阶的块跳过。不对正文按字符硬截，块内顺序和边界规则固定。

| 裁剪次序 | 块与目标台阶                    | 块内移除顺序                                                                   |
| -------- | ------------------------------- | ------------------------------------------------------------------------------ |
| 1        | 日摘要 500 → 0                  | 最旧日期先整块退出                                                             |
| 2        | 跟进 500 → 0                    | 先不相关、再尚未到期、再更远 dueAt；同级 ID                                    |
| 3        | 工具交换 2000 → 1000 → 0        | 只退出最旧已闭合交换组；活跃组不动，无法到达台阶则跳过                         |
| 4        | 近期原文 4000 → 2000 → 1000 → 0 | 最旧完整 Run 组先退出，记录摘要覆盖／缺口                                      |
| 5        | 对话摘要 1500 → 750 → 0         | 低相关块先退出；同相关度旧块先退出                                             |
| 6        | 事实 2000 → 1700 → 1000 → 0     | 非置顶按检索反序退出；置顶最后、按创建时间旧者先退出；明确本轮目标事实最后退出 |

系统、当前输入、工具 Schema、活跃工具交换和明确边界从不静默删除。上述可选项全部退出后仍不满足即 `context_budget_exceeded`，不再调用远程压缩碰运气。事实被裁剪时 routeState 保持、实际 mode=budget_limited，完整读取标志为 false；不让暂时的工具增长改变下轮模式。

每轮记录初始各块大小、经历的台阶、最终 ID／修订、缺口和原因。可选块稳定排序；重复来源优先保留更精确的原文。MEM-T16 固定测试常规 22612、仅日摘要退出即够、跨到近期原文台阶、活跃工具组超限、全部可选清空仍超限，以及中文粗估与 emoji 场景。同输入和同快照必须产生同裁剪结果。

### 8.3 每个模型 Step 前检查

当前代码只在 Run 开始构造上下文；目标在每次模型请求前检查真实 transcript 大小。新增工具结果或输出使其增长时，重新做有界投影，不重新执行工具副作用。

首版不在前台同步调用远程模型压缩整个 transcript。工具节选、旧交流组退出和已存在摘要足够时继续；必选内容仍放不下则结束为 `context_budget_exceeded`。这与“达到阈值就立即做一次远程全压缩”的 coding agent 机制不同，适合当前短工具链和聊天延迟目标。

dailyTokenBudget 继续限制每日调用开销；它不是上下文窗口。摘要、提取仍计入现有模型用量；本地编码另外记录资源指标。

### 9.1 固定模型协议

| 项目         | 规格                                                                      |

| revision     | 614241f622f53c4eeff9890bdc4f31cfecc418b3                                  |
| 输出         | 384 维 float32，有限数值、L2 归一化                                       |
| 查询前缀     | `query: `                                                                 |
| 文档前缀     | `passage: `                                                               |

| 最大编码长度 | 512 tokenizer token，包含前缀与特殊符号                                   |
| 装载         | 固定本地权重，离线加载、trust_remote_code=false                           |
| modelKey     | 模型及 commit、tokenizer、前缀、池化、精度、维度、切分策略版本的稳定 hash |

这些编码约束与[固定版本作者模型卡](https://huggingface.co/intfloat/multilingual-e5-small/raw/614241f622f53c4eeff9890bdc4f31cfecc418b3/README.md)一致。分块属于本项目的补充策略；不能沿用模型示例中的静默 truncation 处理所有记忆。

### 9.2 Worker 与队列

业务和数据库继续由 TS Harness 管理。编码使用一个应用级 Python 常驻子进程，复用实验已测的 Torch/Transformers 组合；专用环境锁依赖，不使用实验脚本直接连接正式数据库。TS 端封装 `EmbeddingPort`，测试可注入确定性实现。

进程以绝对解释器路径和参数数组启动，不拼接 shell 字符串。JSONL 协议带 requestId、scope、run/job 身份、modelKey、deadline 和文本；stdout 仅协议，stderr 仅无正文的诊断。响应校验 requestId、版本、维度、数值和归一化，不能仅信任 Python 进程。

初始单模型计算串行，查询高于后台索引；相同 bot 的失效查询从等待队列删除。队列上限 16 项，每 bot 至多 1 个等待中的前台查询，其他查询可直接回退。后台按 bot 轮转，以**预计单批 P95 不超过 50 ms** 为调度目标，不使用“8 条”作为默认批次。

先在当前 CPU/MPS 设备按 token 长度桶做单条探针，默认每批 1 条；只有已测 P95 乘 1.5 余量仍在 50 ms 内才合批，最多 8 条仅作内存安全上限。短片段和接近 512 token 的长片段不拼同批。每批前检查前台队列和取消，查询存在就让行；不把整个历史回填先一次性送进 Python 内部队列。

如果单个长片段本身超过 50 ms，不能声称可以在 50 ms 抢占：仅在至少 2 秒无前台工作且队列空时调度一个，前台输入到来立即暂停后续索引。单条超时仍可能造成一次降级，必须单列测量；若该设备在在线回填下持续不达标，暂停在线回填，改为空闲维护期预建索引并记录不支持的并发形态，不默默把前台普遍回退当成功。

初始查询截止为从 TS 接受检索到结果可用的 250 ms，包含排队、编码和扫描的异步等待；权威 DB 同步读取另行监测，不能将该截止宣传成任何负载下的硬实时保证。超过截止即回退，迟到结果丢弃。

模型加载与预热不占前台检索截止。全量记忆块达到约 75% 预算、或首次进入 hybrid 时在后台预热；权重缺失则继续关键词并在维护页显示“语义检索未就绪”，不在聊天请求中下载模型。

查询取消先释放调用者和移除排队工作，不能声称已立即中断底层 kernel。运行任务超过 5 秒无响应时重启 worker，受影响查询回退；10 分钟内失败 3 次则暂停重启 60 秒。上述为故障控制起点，需要压力验证。关闭应用或归档 bot 时释放对应任务；共享模型只在无消费者或进程退出时关闭。

首版余弦扫描放 TS `worker_threads` 计算队列，矩阵**常驻计算线程**，按 scope/modelKey 分区。首次装载用 transferList 转移 ArrayBuffer，此后仅传新增／替换／删除行和 generation，不逐查询复制 25000×384 的矩阵。查询仅传约 1.5 KiB 查询向量、有效行 bitmask（25000 行约 3.1 KiB）、scope 和 generation；返回候选 ID／修订。首版不需要 SharedArrayBuffer 或锁协议。

主进程负责资格与最终水合，计算线程不直接读写事实库。矩阵 generation/indexVersion 与事实 memoryVersion 分开；索引 ready 只更新前者。删除或失效通知到来排除有关行，即使通知迟到主进程仍会拒绝失效候选。扫描测速必须包括 query 消息传输、排队和候选返回，不能用纯点积耗时替代。

### 9.3 长记忆分块

先按完整句段切分，每个片段编码后检查长度。只有单句段超过窗口时，使用约 256 token、32 token 重叠窗口；最终带前缀与特殊符号的输入必须小于等于 512。不能仅按字符数判断模型长度。

片段记录 memoryId、memoryRevision、chunkId、原文起止和 textHash。召回时按事实聚合，必要时加入相邻否定、时间和主体限定句。如果加入限定句后预算放不下，返回来源展开提示或丢弃该节选，不能只留下脱离条件的肯定句。

完整原文仍在 `memories` 表；向量表不重复保存完整正文。遗忘要清片段、向量和缓存，不能把向量当成不含个人信息的普通指标。

### 9.4 索引一致性

索引 Job 捕获 scope、epoch、memoryId/revision、sourceFingerprint、textHash、realityScope 和 modelKey。编码在事务外执行；写回前重查所有字段及当前资格，一项变化就拒绝该结果。

新增、确认、更正、有效期改变在事实事务中写 `memory_index_state` 的 dirty 标记。worker 成功后在短事务中替换该事实的完整片段集合并标 ready，不能先删一半再暴露半成品。ready 绑定 revision/modelKey，模型升级全部视为待重建。

到期由读取资格即时生效，清理任务随后移除索引；不能依赖定时器准时运行保证不返回过期事实。缺索引、部分索引和 worker 失败都不影响事实事务提交。重启按 dirty 状态及有效事实差集继续，处理来源时分页，不一次把全部正文送入模型。

## 10 数据模型和 SQLite 迁移

### 10.1 保留与扩展

继续使用现有 messages、runs、sources、memories、followups、series、deliveries、jobs。旧 JSON 可读，新增字段提供明确默认值；不将 AI SDK 消息类型作为存储 Schema。

| 对象        | 新增字段或扩展                                                                                                                   |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Run/Message | segmentId；消息展示与内容身份校验元数据                                                                                          |
| Memory      | realityScope、subject、predicate/topic、episodeType、learnedAt、EvidenceRef、derived、coverage；不改变已有 id 和 previousId 语义 |
| Job         | 增加 segment_summary、memory_index；payloadVersion、strategyVersion、稳定输入指纹与幂等工作键                                    |
| Settings    | 读取策略和摘要开关的版本化默认值；关闭向量不关闭事实读取                                                                         |

新增表的所有键和查询均带 owner、relationship。下表为必须字段，实施时用显式迁移和约束固化：

| 表                     | 字段与唯一约束                                                                                                                      | 用途                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| memory_state           | owner/relationship 主键；memoryVersion、contextVersion、indexVersion、routeState、routingPolicyVersion、updatedAt                   | 三种版本分离，递增清单见 10.3；保存路由滞后状态                                           |
| conversation_segments  | scope、id、firstSeq、lastSeq、startedAt、lastUserAt、status                                                                         | 每段身份与排序；同 scope 只允许一个可接受输入的 open 段                                   |
| conversation_summaries | scope、id、segmentId、rangeKey、inputRefs、inputHash、policyVersion、text、coverage、status、rebuildBlocked、revision、createdAt    | 同 scope/rangeKey/policyVersion/inputHash 唯一；旧版 superseded，删除保留非内容禁重建标记 |
| memory_dependencies    | scope、dependentType/id/revision、inputType/id/revision、sliceHash                                                                  | 反查更正和遗忘影响的摘要、事件、事实；输入键建索引                                        |
| memory_embeddings      | scope、memoryId/revision、chunkId、spanStartUtf16/spanEndUtf16、textHash、sourceFingerprint、modelKey、dimension、vector、createdAt | scope/memoryId/modelKey/chunkId 唯一；dimension=384、BLOB=1536 字节，有限数值在入口验证   |
| memory_index_state     | scope、memoryId、wantedRevision、modelKey、status、attempts、nextAt、reason                                                         | scope/memoryId/modelKey 唯一；dirty/ready/failed，故障不改事实状态                        |

另新增 conversation_summary_fts，索引 scope、summaryId、topic/entity 和摘要正文，与摘要提交及遗忘同事务维护；事件继续复用 memory_fts。原文切片和向量位置全部采用 UTF-16，最终字段名为 spanStartUtf16/spanEndUtf16。

sourceFingerprint 使用按稳定顺序序列化的来源 ID、修订、限定范围 hash；不能只 hash 正文。依赖表记录的是可删除的内部元数据，不能把原文混进 JSON 日志。Source 与助手消息的证据校验集中在 `EvidenceResolver`，不让各模块自行解释。

删除台账也需要显式版本兼容：当前 `files.ts` 使用 strict Schema，只接受 sourceIds/memoryIds，不能直接添加字段假定旧读取器会忽略。新版读取器同时支持 v1 记录与 v2 记录，v2 增加 summaryIds 和 summaryBlocks；后者只保存摘要 ID、输入消息 ID 集合及策略标识，不保存正文。恢复合并同一删除项时合并这些目标，不能丢失新字段。

### 10.2 版本和回填

当前 `PRAGMA user_version=1`，目标增量版本为 2。先实现真实的逐版本迁移入口，再在短迁移事务中创建新表和索引、更新版本；重型回填不在迁移事务里调用模型。

1. 对已有数据做一致性备份，保留现有删除台账；记录迁移前版本。
2. 停止该 bot 新输入和后台写入，完成 Schema 事务；失败回滚且拒绝半迁移服务。
3. 用兼容读取器解释旧 JSON；已存在 day 摘要映射 daily，其他 episode 按来源保守映射，不编造时间、主体或现实范围。
4. 建立 memory_state，按现有有效事实分页填 dirty 索引标记与依赖元数据。缺依赖的旧派生内容先保守失效或不用于权威推断。
5. 旧对话的 segment 归属分页回填，当前范围优先；不自动抽取全部私人历史或批量生成远程摘要。
6. 通过核对后开放词法／全量聊天，再后台索引。模型缺失不阻塞 Schema 迁移和基本聊天。

现有 `Store` 拒绝高于 1 的库，需要与 restoreBackup 一起升级支持 2；不能只改常规启动入口。所有新表必须加入导出、遗忘和恢复清理。JSON 字段兼容测试要覆盖没有新增字段的旧库。

本阶段只支持新二进制通过 feature flag 关闭新读取／摘要、保留新 Schema 的回退路径。不实现自动生成 v1 兼容删除清单的逻辑。旧二进制会拒绝版本 2，不允许调低 user_version 硬启动。

确需回到旧版本属于人工恢复：先隔离迁移前备份，人工核对并应用截至当前的删除目标、核对迁移后新写入会丢失的范围，完成恢复核验后再开放服务。旧读取器不能直接读取 v2 strict 删除清单；保留原台账，未完成兼容性及删除核对前不得启动。文档不承诺该人工流程自动无损，也不因简化回退而允许删除内容复活。

### 10.3 版本递增清单

版本只提示可能变化，最终仍核验选中对象的当前来源和修订。一个事务每种版本最多加 1，不能每写一行就加。规则如下：

| 写操作                                             | memoryVersion  | contextVersion          | indexVersion／其他                                  |
| -------------------------------------------------- | -------------- | ----------------------- | --------------------------------------------------- |
| pending 候选创建、提示、暂缓、过期、超量退出、丢弃 | 不变           | 不变                    | lifecycle 元数据；若确实删除来源，按遗忘行处理      |
| 确认／人工新增 active 事实；更正；撤回有效事实     | +1             | 仅有受影响摘要失效时 +1 | dirty 标记不另递增 memoryVersion                    |
| active 事实置顶、主体、范围、有效期或来源资格修改  | +1             | 有关上下文受影响时 +1   | 资格变化须重新试算路由                              |
| 对话摘要／事件创建、替换、失效；展示前缀新增       | 不变           | +1                      | 选中切片仍有效时无须重建整轮                        |
| 索引 dirty→ready、向量重建、worker 装载与重启      | 不变           | 不变                    | indexVersion/generation 更新；不能终止 Run          |
| 改路由策略、模型版本、预算配置                     | 不变           | 不变                    | routingPolicyVersion/indexVersion；按配置边界捕获   |
| 删除来源／已确认记忆／摘要并应用删除台账           | +1             | +1                      | epoch +1，索引失效，当前读取取消                    |
| 跟进、工作状态、人格或边界变化                     | 不因该操作递增 | 按选中状态单独复查      | 沿用各自 revision、boundaryRevision/personaRevision |

仅时间流逝导致 validFrom/validTo 越界不必伪造写事务；快照记录 nextEligibilityBoundary，异步返回后检查当前时刻，必要时重做资格选择。routeState 只在事实集合实际变化时按 7.3 重算，不因 index ready 反复切换。

## 11 更正 遗忘 与备份恢复

### 11.1 更正事务

更正明确目标和 expectedRevision 后，在同一事务中结束旧事实、写新事实及确认来源、更新依赖失效、dirty 索引和 memoryVersion。冲突主题的具体对象按第 6 节判定。

提交后使旧缓存不可用，终止正在用失效证据生成的 Run 或 Job；新事实经 delta 立即可读。更正不必递增删除 epoch，旧任务仍须因 revision/sourceFingerprint 不符而拒绝。

跨异步步骤后，按 10.3 区分版本。memoryVersion 改变先校验实际选中来源；无关变化可继续，但 all 路径须复核是否漏掉新增事实。contextVersion 改变仅对当前选中摘要／切片做核验，不因后台新建无关块终止；indexVersion 变化不触发上下文重建。初次模型调用前对实际影响证据的变化最多重建 1 次，再次出现影响当前证据的变化才结束为 `memory_snapshot_changed`。已有可见输出后不透明重试重写，保留已展示部分并结束旧生成。

### 11.2 遗忘闭包

沿用非内容删除台账先落盘、数据库幂等应用的顺序，新增内容进入相同闭包：

```text
来源或记忆撤销
  → 原文／事实失效
  → 依赖摘要和事件失效并清正文
  → 关联向量片段和 dirty/ready 状态删除
  → resident 矩阵、Run 投影、worker 待处理正文和工具缓存清理
  → 关联跟进／投递、内容型 Trace、事件和导出按现有规则清理
  → epoch 推进，客户端旧快照失效，迟到结果拒绝
```

首版限制为固定两层依赖：根来源／已展示消息 → 事实、摘要或事件 → 事实向量。摘要和事件持久依赖展开到根证据，不依赖另一个摘要；EvidenceRef 的 memory/summary 类型可用于读取，但落持久依赖时必须展开并校验根来源。不实现通用递归遍历或任意依赖图。

应用失效时先按根来源／消息反查第一层，再清受影响事实的向量；最多两跳。遇到未知边类型、摘要依赖摘要或层次异常时，保守清当前 bot 的派生摘要、向量和缓存并标待重建。读取端核验权威记录，即使索引删除失败也不能召回正文。事务提交后崩溃，重启由台账完成剩余清理并丢弃缓存。

现有删除来源会保守清理该 scope 的助手正文；本阶段先保留这个已测试行为，不在新增记忆功能时顺便弱化它。只删除某条摘要时不删除原始来源，但保存该范围与策略的禁自动重建标记；用户明确重算才解除。新 working summary 也遵循这一规则，不能换 rangeKey 逃避禁重建。

summaryBlocks 按稳定消息 ID 阻止同一原始内容被换一组范围重新归纳，不能仅按可在旧备份恢复后复用的事件序号判断。摘要删除后清 text 和输入节选，仅保留禁重建所需非内容标识；原始消息的普通读取仍可用。用户明确重算通过专门命令解除该范围标记，并记录新确认，不把自动重试当成授权。

### 11.3 备份与恢复

一致性备份包含事实、依赖、段落和摘要；向量表可以随库备份，但恢复时只在当前 modelKey、来源和删除台账均匹配时使用。模型权重、进程内缓存和凭据不打包进数据库备份。

恢复顺序：验证备份 → 合并最新删除台账 → 在私有 staging 目录迁移／应用删除 → 清理失效摘要和向量 → 运行恢复规则 → 原子发布目录 → 后台重建缺失索引。

若已经更正的信息在备份后才发生，更正本身需要新的有效备份或可恢复记录；删除台账只防删除内容复活，不保存所有更正历史。恢复界面要说明备份时间，不能把防遗忘复活扩展成“任何修改都不会丢”。

本地逻辑删除覆盖当前应用、派生表和导出；历史备份、SQLite 空闲页及系统快照的物理清理由独立保留策略处理。Embedding 在本地运行不代表聊天内容从不外发：选中记忆仍会随聊天或摘要请求发送给当前已授权的远程模型；沿用既有外发说明，不扩大为新的服务授权。

## 12 等待状态与用户交互

### 12.1 显示规则

发送后立即显示用户消息已接收。若约 800 ms 尚无可见助手正文，显示“角色名正在输入…”；这个阈值是初始 UI 参数，不是由实验测得的人类固定标准。

首版只保留“角色名正在输入…”与超过约 8 秒无正文时的“这次回复有点慢”两档，不单设“我翻记录”角色化提示。检索是否发生只进诊断，避免短检索闪烁或状态口吻与角色消息混淆。保留停止操作，不编造完成百分比或剩余时间。

状态由 runId 关联的后端阶段与前端计时驱动，不让模型多生成一次“我想想”。实际正文可见、取消、失败、归档或切换角色时清理；断线重连先取当前快照，不回放旧计时器。重新排队、后台提取和后台预热不冒充正在回复用户。

### 12.2 分条回复与语音

当前分条模式会等整段生成后发送，首 token 不等于首段可见。首版保留现有分条策略，等待提示一直持续到首段正式发布；不为了隐藏延迟伪造一条持久“我想想”。是否改为边生成边分段发送属于独立呈现改动，需另做中断和语音验收。

状态不写 messages、sources、摘要或事实，不作为助手共同经历，不进入 TTS 队列，不产生通知。使用轻量 `role=status`、礼貌播报更新，避免省略号动画每帧触发无障碍播报。用户可停止仍是既有 Run 取消命令。

### 12.3 维护页和确认

维护页显示来源、确认状态、时间与现实范围，支持现有确认、更正、暂缓和遗忘。新增语义状态只显示就绪／预热／降级及简短原因，不要求普通用户理解维度、RRF 或 worker 协议。

自动提取不每轮弹确认。第一版同时提供待确认列表与 6.4 的聊天内卡片，按明确资格、机会和配额显示，不另发通知，不把沉默视为确认。确认提示频率属于待验体验，不能以“减少点击”为由绕过事实资格。MEM-C 是与摘要同级的独立交付，不能被本节 UI 附注替代。

## 13 API 事件与诊断

### 13.1 保持已有接口

现有 `/v1/memory` 列表、新增、`/v1/memory/corrections`、`/v1/memory/forget`、导出及 Run trace 保留。管理列表可以展示 pending 和历史版本，模型读取只用合格记录；二者不能共用一个默认过滤器导致管理页看不到待确认内容。

GET `/v1/memory?q=...` 保持兼容的数组型管理查询合同。新增 POST `/v1/memory/search` 提供结构化读取结果，参数只含 query、target 和受限游标／数量，不接受客户端声称的 owner、数据库路径或模型版本。服务端解析 bot 和作用域；向量和正文不进入公开事件。

`/v1/memory/forget` 增加可选 summaryIds，旧请求不变；新目标先按作用域验证，再进入同一删除台账和失效流程。增加受保护的摘要列表／来源读取与 `summary.rebuild` 管理命令，重建要求明确目标及 expectedRevision。不得让模型工具自行解除用户的禁重建标记。

`search_memory` 保留 query 必填，新增可选 target，默认 facts；旧调用仍有效。增加只读 `read_memory_source` 工具供受限展开已召回来源，每次最多 1000 token、必须重新检查授权和有效性。sourceId 必须来自本 Run 已提供的候选或直接相关的当前来源，不开放任意 ID 扫库。两个工具都计入当前 Run 上限。

### 13.2 公开状态与诊断分开

可新增 `run.phase`，字段仅 runId、phase、阶段序号和时间，phase 为 queued/preparing/recalling/generating/sending/terminal。仅实际阶段变化时发送，不每次扫描发事件，不包含查询、工具参数和匹配正文。

阶段是展示信息，恢复后以当前 Run 快照为准，不以 SSE 事件重建模型记忆。`run.accepted`、`run.started` 和终态保持既有含义；阶段不改变幂等键和投递合同。

内部 trace 新增以下元数据：

- readMode、目标范围、资格数量、索引覆盖、实际纳入 ID／修订、排除原因、epoch、memoryVersion、policyVersion；
- queue/encode/scan/hydrate/context 总时长，cacheReady、coldStart、fallbackReason；
- 按块估算 token、整体估算与实际 usage、摘要覆盖范围和缺口；
- 输入接受到模型首 token、首段可见／客户端展示回执、完成的分别计时。

默认诊断不复制 query、全文 prompt、原始事实或编码输入。现有用于本地检查的内容型上下文保持可清除，新增诊断不能再创建脱离遗忘清理的日志。客户端展示回执不等于用户已阅读，指标注明它的实际含义。

## 14 性能目标与故障合同

### 14.1 已有证据及边界

实验详见研究文档及 memory-lab 原始结果：

| 项目              | 已有结果                                        | 不能外推的部分                                   |
| ----------------- | ----------------------------------------------- | ------------------------------------------------ |
| 10 条事实全量读取 | 受控问答 16/16，关键词 8/16                     | 不是长期真实聊天准确率                           |
| E5 混合首轮验证   | 关键词 16/16、换说法 31/32、问答 62/64          | 没有完整人格、历史和工具链                       |
| E5 新主题确认     | 问答 48/48                                      | 只有 16 个新目标主题，不能宣称 100% 可靠         |
| E5 查询编码       | P50 约 11 ms；两轮 P95 约 63–210 ms             | 不含完整检索、队列、数据库和远程回答             |
| E5 加载与资源     | 约 2.21 s，进程峰值 RSS 约 894 MiB              | 冷启动不应进入前台等待；不是所有设备保证         |
| 常驻扫描          | 5000 个向量 P95 约 1.98 ms；25000 个约 11.29 ms | 性能向量是重复／微扰集，不衡量语义质量或完整水合 |

对“未出发能否回答住了几晚”等审计样本，生产评估应明确所问是否限定本次计划旅行；不能仅凭未出发推断用户一生没有在当地住过。字符串或固定别名评分只作辅助，含歧义、否定和推导的样本需保留解释及逐项复核。

### 14.2 初始上线目标

同机、单用户、热 worker 和可比较事实规模下，全量路径上下文准备 P95 目标 100 ms，正常混合完整准备 P95 目标 300 ms；语义异步等待上限起点 250 ms。首次超时正常降级，不能为凑目标隐藏失败查询。

完整性能报告至少覆盖 50/500/5000/25000 条合格向量、不同文本长度、缺索引比例和多个 bot 并行；另外测大规模不合格记录的过滤成本。每组热查询至少 100 次，报告 P50/P95/P99、样本数和设备，冷启动至少 5 次单列。P99 在小样本下只作描述，不当成稳定保证。

必须加入“后台索引进行中的前台查询”组：分别在 CPU/MPS，用接近 512 token 的长片段持续回填，在批次随机位置插入前台短／长查询，至少 100 次；报告排队、编码、扫描 IPC、总时长及 250 ms 降级率，对照无回填组。回填组降级率初始目标不超过 5%，且比空闲组增量不超过 3 个百分点；这是工程发布门槛，不是已有实测。单长片段超时、暂停回填、进程重启单列。未达标则调整批次／暂停在线回填，不能剔除超时样本或只报告单条短查询中位数。

首段可见时间以相同回答模型、人格、历史、输出模式比较旧策略与新策略；报告普通／分条两种模式，至少 30 个问题，包含超时和弃答。语义检索收益不能以明显拖慢普通聊天为代价，偏离目标需登记原因后调整。25000 条之外和未来公网并发不作容量承诺。

### 14.3 故障处理表

| 故障                     | 行为                                        | 持久结果                        |
| ------------------------ | ------------------------------------------- | ------------------------------- |
| 权重缺失／预热未完成     | 关键词或全量照常；后台就绪检查              | 不改事实状态                    |
| 编码超时／异常／错误维度 | 丢弃响应并降级                              | 记录不含正文原因，索引可重试    |
| 查询期间更正             | 拒绝旧证据；按版本规则有限重建              | 新事实立即有效                  |
| 查询期间遗忘／取消       | 结束调用；不再触发回退工作                  | 迟到返回无权写入或展示          |
| 摘要失败／预算耗尽       | 保留旧有效摘要与原文退路，登记缺口          | 游标不推进，不覆盖旧摘要        |
| 索引写入失败             | 事实和 dirty 标记仍存在                     | 重启可继续，不能留下 ready 假象 |
| 进程重启                 | 前台 running 中断；后台固定输入任务幂等恢复 | 不重发已展示回复或通知          |
| 数据库／删除清单损坏     | 拒绝继续以该状态服务                        | 不自动创建空人格或空记忆替代    |

## 15 模块落点与依赖方向

目标新增目录以小模块逐步提取，不为文档一次建立完整框架：

```text
src/memory/
  contracts.ts             读取结果、EvidenceRef、策略版本
  eligibility.ts           事实／事件／摘要资格与最终校验
  evidence.ts              来源与消息可见片段解析
  retrieval.ts             all／hybrid／keyword／structured 编排
  budget.ts                序列化计数与有界节选
  conversations.ts         内部分段、摘要范围和覆盖
  consolidation.ts        提取、确认、冲突、事件规则
  embeddings.ts           EmbeddingPort 与任务身份
  embedding-process.ts    Python 子进程协议与生命周期
  embedding-worker.py     固定 E5 编码，不访问事实数据库
  vector-scan-worker.ts   隔离矩阵与精确扫描
  migrations.ts           v1 到 v2 的增量 Schema
```

`Store` 掌握同步 SQL、短事务和作用域。`Harness` 掌握 Run/Job 的准入、预算、取消与提交；retrieval 不自行续跑聊天。model.ts 继续仅负责聊天提供方协议；E5 不通过聊天 SDK 调用。BotManager 注入共享计算资源，每 bot 维护自己的 Store 和领域服务。

既有修改范围：domain.ts 增加兼容字段；store.ts 接迁移、资格访问和依赖删除；files.ts 接删除台账版本；context.ts 拆准备与纯投影；harness.ts 接异步工具与新 Job；bots.ts 管计算资源引用；backup.ts 加恢复校验；server.ts 加读取入口和只读状态；web/app.js 加临时状态与必要来源展示。

新增 `requirements-memory.txt` 或等效锁文件，独立配置 Python 绝对路径、固定模型目录和可关闭向量开关。安装和权重准备有可复现命令，启动不自动修改用户全局 Python 环境。研究脚本保留为离线评估，不从 scripts/memory-lab 导入正式业务实现。

### 17.2 质量评估

沿用首轮校准／验证、独立新主题和少量事实数据，保持原始输出、审计规则和模型版本。扩充至少 20 组固定多轮场景，覆盖上表的时间、主体、指代、更正和冲突；问题定义先固定，再运行新策略，不能看失败后改标签凑通过。

区分来源召回、答案正确、无答案弃答、摘要信息保留与用户体验。精确关键词不得比旧基线退化；同一冻结验证集的换说法召回应明显优于词法。研究中的 E5 31/32 与 16/16 是回归参考，不对真实用户分布承诺该比例。

完整 Harness 质量实验分别测已配置的回答模型，保留相同人格和预算对照；真实 API 运行单列次数和用量，不在普通单元测试里付费调用。真实私人聊天不自动纳入评测或发给新服务。

### 17.3 发布清单

通过类型检查、相关单元和全项目回归、生产构建、浏览器等待与分条／取消场景；通过迁移、备份恢复和删除故障注入；复跑记忆实验并完成热冷延迟报告。对逻辑泄漏、更正旧值和删除复活保持零容忍。

在独立临时数据目录用正式应用构造路径启动验收，不修改正在运行的关系库。产品门槛未决定实施 E5 时，发布范围明确为基础记忆版，向量与 worker 测试标为未实施。开启向量版才检查固定权重、依赖环境、回填延迟和离线回退；迁移前备份，核对人格、消息数、事实、删除 epoch 和索引覆盖。

发布后观察降级率、摘要失败／缺口、候选积压、取消回收、首段可见延迟与不支持断言。第一轮至少收集 7 个自然日的实际使用反馈，人工评估连续性；工程测试通过不标记陪伴体验已经成熟。出现数据正确性问题先关新读取／摘要功能并保留证据，不能靠提高相似度阈值掩盖。
