# 角色生活系统工程方案

版本：v0.1 · 日期：2026-10-24（Asia/Shanghai）· 状态：待实施的工程设计。

本方案依据当前源码及本轮已明确的产品方向：每个角色生活在贴近现实的虚构世界中，有自己的设定、日常作息、每日安排、事件和记忆。分条回复与发送间隔已存在；本文件不表示角色生活功能已经实现。本轮只新增设计文档，不修改运行配置、角色设定或业务代码。

## 1. 产品合同与实施范围

核心闭环：

**角色设定 → 日常规则 → 今天的计划 → 当天实际发生的事件 → 角色记忆与状态 → 下一天的选择。**

生活状态贯穿真实日期，角色在不同对话里引用同一份已经确定的经历。用户的明确互动能够影响尚未发生的安排。

第一版交付角色生活闭环：设定发布、routine、当天计划、活动推进、角色自己的事件和记忆、聊天读取、暂停／恢复、隔离与故障语义。主动分享和编排型故事线分阶段增加，分别有独立开关。

生活本身已经有跨天连续性：昨天未完成的工作、上次做菜的结果可以影响今天。额外的「跨天故事」开关仅控制有主题和节拍的剧情编排；关闭它不会使基础生活每天清零。

## 2. 现有工程的接入位置

当前为 TypeScript、Node.js、Fastify、SQLite、自有 Harness、模型端口及 HTTP/SSE。继续使用现有依赖，不新增完整 Agent 框架、向量服务或多角色社会模拟。

| 当前文件／边界 | 已有能力 | 本次设计的接入方式 |
|---|---|---|
| `src/bots.ts` | 每个 bot 独立数据目录、Store、Harness，归档时释放运行资源 | 每个 Harness 持有一个 LifeService；归档同步暂停其任务 |
| `src/domain.ts` | Persona、Settings、Message、Run、Memory、FollowUp、Delivery | Settings 加可选功能；生活领域类型放在独立目录 |
| `src/store.ts` | SQLite、事务、作用域、版本、恢复、删除清单 | 增加显式 schema migration；生活数据由 LifeStore 管理 |
| `src/schedule.ts` | Temporal 与 IANA 时区的日／周排程 | 复用时间换算方式，新增角色 routine 编译器 |
| `src/harness.ts` | 前台优先、后台取消、预算、来源检查、Outbox | 调度生活任务，提供有界模型调用和提交栅栏 |
| `src/context.ts` | 人格、状态、记忆和历史投影，保守展示回执 | 生活开启时增加独立角色生活数据块 |
| `src/model.ts` | 模型端口、规范化事件、取消、usage | 新增生活用途枚举，不让生活模块直接依赖提供方 SDK |
| `src/server.ts` | 本地认证、CSRF、bot 选择、版本化接口、SSE | 增加当前角色的生活接口及更新事件 |
| `src/backup.ts`、`src/files.ts` | 一致性备份、删除清单、恢复 | 增加生活数据的遗忘、导出和恢复合同 |
| `web/app.js` | 设置、聊天、分条消息、串行朗读 | 增加生活设置／只读时间线，保持聊天入口 |

当前后台 Job 只有 extract／summary，FollowUp 是用户事项，Source 只有 message／manual。生活任务、事件来源不能伪装成这些实体，也不能通过虚构用户输入启动对话。

## 3. 必须成立的不变量

1. 新功能按 bot 独立，默认关闭；关闭时不注入生活提示词、不发起生活模型调用、不创建生活任务。
2. 角色经历与用户事实属于不同数据域，不能因同属一种 Memory 文本而混用。
3. Routine 是可重复规则；DayPlan 是未来意图；LifeEvent 是已经发生的记录。
4. 同一活动只产生一次有效结算；重复 tick、刷新、重启都不能重复发生。
5. 明确的过去不能在下次生成时悄悄改写；修正通过有版本的更正记录表达。
6. 角色自己的活动可以自主推进，涉及用户参与的活动需要对应的互动证据。
7. 事件提交、状态更新及必要记忆投影必须保持原子一致性；模型调用不在数据库事务中等待。
8. 生成期间设定、来源、开关或世界代数已变化，旧结果不得提交。
9. 发送、向用户表达、客户端展示与用户参与分别记录，不能用一个 shared 字段混合表达。
10. 前台聊天优先。活动繁忙程度可以影响表达，但第一版不据此拒绝聊天或故意延迟用户的问题。

## 4. 模块与依赖

建议新增：

```text
src/character-life/
  domain.ts          领域类型与 Zod 合同
  profile.ts         生活设定草稿、校验、发布
  routine.ts         周规则、例外日期、跨日时段编译
  planner.ts         当天候选计划与约束校验
  resolver.ts        活动开始／结算、状态效果与因果检查
  memory.ts          角色记忆投影、召回、来源失效
  service.ts         生命周期、推进、版本检查与统一入口
  store.ts           本作用域的生活数据访问
  context.ts         聊天需要的只读生活快照
  sharing.ts         后续主动分享候选与准入
```

LifeService 依赖作用域 Store、Clock 和 Harness 提供的有界模型调用端口。它不能拥有独立无限循环，不能直接发送网络消息，也不能直接修改 Persona 或用户记忆。

Harness 负责执行机会、预算、取消和调用记录；LifeService 负责生活领域决策与事务；网页负责显示和操作。

## 5. 数据模型

每条生活数据继承 `ownerUserId + relationshipId` 作用域，并保存 `worldId`。一个 bot 在该关系下最多有一个当前生活世界；显式重置才创建新 worldId。角色模板不能共享各自的生活记忆。

第一版建议六张生活表，复用现有 SQLite，不单独部署数据库。JSON 适合保存有界计划、约束和小型状态；幂等键、作用域、时间及状态等查询字段单独建索引。

| 表／实体 | 核心内容 | 角色 |
|---|---|---|
| `life_profiles` / LifeProfile | 版本、关联人格版本、职业、住处、固定人物地点、routine 规则、允许的活动、初始目标 | 用户发布的生活规则，历史版本保留 |
| `life_days` / DayPlan | 当地日期、时区、计划版本、输入版本摘要、固定 seed、稳定 activityId、时段、前置条件、参与方式 | 当天的意图，不是已发生事实 |
| `life_events` / LifeEvent | 活动身份、事件类型、时间、事实结果、状态效果、来源、更正关系、幂等键 | 已发生事件的权威记录 |
| `life_state` / LifeWorld | 世界控制状态、lifeEpoch、当前设定、状态修订、推进游标、位置／当前活动／未完目标等投影 | 控制信息持久化，生活状态可按事件重建 |
| `life_memories` / LifeMemory | 事件／设定来源、记忆文本、重要度、情绪余韵、已整理游标、修订与失效状态 | 可重建的角色记忆，不是用户画像 |
| `life_jobs` / LifeJob | 用途、幂等键、捕获版本、输入摘要、状态、重试、usage 引用、截止时间 | 持久的有界工作单，由现有 Harness 调度 |

后续故事编排才增加 `life_arcs`，主动分享增加 `life_share_intents`，避免第一版提前引入完整剧情平台。

### 5.1 生活设定

人格继续拥有姓名、身份、说话方式和相处方式，LifeProfile 不另建一套可以独立漂移的人格。

LifeProfile 补充：

- 职业、工作方式、必须承担的责任；
- 住处、同住关系、常去地点及主要路程；
- 少量固定配角，保存稳定 ID、关系、活动约束；
- 工作日／休息日作息、可变时间窗、休息需求；
- 经济／行动范围等影响选择的限制；
- 一到两个当前个人目标及初始世界状态。

角色已有信息不足时，可以生成一次生活设定草稿供编辑发布。不得自动给现有角色加职业、家人、重大过去或新关系。发布后，授权世界规则内的普通日常可自动生成，无需每天确认每一餐。

背景过去与运行后经历分开：用户批准的背景可以成为 `backstory` 记忆，不能伪造成系统在启用前运行过的每日事件。

### 5.2 Daily routine 与每日计划

Routine 规则保存稳定 ruleId、适用星期／日期、当地时间窗、持续时间范围、地点、必要资源、刚性程度和活动类别。

例如工作是刚性时段，看电影是可移动意图。睡眠跨午夜、通勤需要时间，活动总时长不得超过时间窗。第一版只保存会实际影响选择的资源约束，例如「没鸡蛋」或「作品未完成」，不模拟完整购物账本。

DayPlan 的活动至少包含：

```ts
type PlannedActivity = {
  activityId: string; // 由程序分配，重试不重新随机生成
  ruleId?: string;
  title: string;
  category: "obligation" | "routine" | "personal_goal";
  startAt: number;
  endAt: number;
  locationId: string;
  participantIds: string[];
  userParticipation: "none" | "invited" | "agreed";
  requiresUserPresence: boolean;
  preconditions: Condition[];
  importance: "ordinary" | "notable";
};
```

Condition 是限定字段与操作符的 Schema，不执行模型提供的代码或 SQL。是否已经开始／结束由事件投影得出，不能仅凭计划时段判断活动已完成。

### 5.3 事件与时间

事件类型先限制为 `activity_started`、`activity_resolved`、`activity_cancelled`、`plan_adjusted`、`goal_updated`、`event_corrected`、`world_resumed`。

一条事件至少有：

```ts
type LifeEvent = {
  id: string;
  worldId: string;
  occurrenceKey: string;
  activityId?: string;
  type: LifeEventType;
  profileRevision: number;
  planRevision?: number;
  occurredAt: number;
  recordedAt: number;
  origin: "routine_simulation" | "chat_interaction" | "offline_reconstruction";
  participantIds: string[];
  summary: string;
  effects: AllowedStateChange[];
  sources: LifeSourceRef[];
  supersedesEventId?: string;
};
```

计划时间在 DayPlan；发生时间是世界里的时间；recordedAt 是系统提交时间。离线重建另有 origin，不能把恢复时合成的事件说成后台当时已执行。

`occurrenceKey` 基于 worldId、当地日期和稳定活动身份，数据库对作用域、worldId、occurrenceKey、事件类型建立唯一约束。计划修订不能换一组 ID 重新执行已经发生的活动。更正追加独立记录，原发生身份仍占用，删除时也保留不含正文的去重标记。

### 5.4 事实、感受与记忆

LifeEvent 保存「发生了什么」；LifeMemory 可以保存该事件留下的感受和总结。感受属于角色体验，不升级为对用户情绪或第三方心理的事实判断。

普通活动可以只留下当天压缩记录；有结果变化、个人目标、人际后果或后续价值的事件才进入较长期记忆。不需要永久保存每天每一顿早餐的独立摘要。

最小事件记忆与事件在同一事务中生成；每日自然语言整理是可重试的投影，整理结果和处理游标一起提交。记忆失效不使原始事件重复发生。

现有用户 Memory 保留自己的确认规则；生活模拟的有效事件可自动成为角色记忆。`autoExtract` 继续控制用户记忆提取，不用它来关闭生活的基本记忆能力。

## 6. 正确一天的生成与推进

### 6.1 初始化

1. 保留旧 bot 当前人格、聊天和记忆。
2. 编辑／发布 LifeProfile，生活默认仍关闭。
3. 用户开启角色日常后创建当前 worldId，记录开始时间与初始状态。
4. 编译当前日期剩余时段的可用计划；启用前的时间不伪造为运行经历。
5. 世界处于 preparing 时可以使用确定性的基础作息，模型变化计划在后台准备；网页显示准备状态。

### 6.2 生成当天计划

输入仅取已发布设定、有效 routine、昨天的必要结果、未完目标、已有约定及当前世界状态。

先由程序排刚性事项、睡眠和必要移动；模型只在剩余可用时间里提出少量可变活动，并说明关联目标和所需条件。程序为活动分配稳定身份并校验：

- 时间没有重叠，持续时间和移动时间可行；
- 所引用人物、地点、物品和目标存在；
- 已承诺的事项没有被静默删除；
- 用户未同意的邀请没有变成共同活动；
- 活动符合角色身份、责任与当前资源；
- 相同输入版本没有创建第二份当前计划。

模型返回非法计划时不做无限修复：允许至多一次受预算约束的修复，再使用基础 routine；不会为了显得丰富硬塞活动。

计划版本不可原地覆盖历史：保留旧版本，新版本只替换未来部分；已经开始或结算的活动保留身份和事实。

### 6.3 推进活动

到开始边界，检查前置条件并提交开始事件；到结算边界，根据实际状态产生结果。用户必须参与的活动不会因时间到了就自动完成。

基础睡眠、通勤、普通用餐等活动可以用规则模板结算。少量值得展开的活动交给模型，在有限结果类型中描述完成／部分完成／延期／取消及合理细节。

个人目标允许继续、受阻或改变。模型不得直接更新任意状态：AllowedStateChange 只允许修改已登记目标、当前活动、位置、限定资源与角色短期感受；不允许更改人格、用户事实或凭空创建重要人物。

模型可提出新增配角／重大生活变化，但第一版作为设定建议，等用户发布后再生效。普通场景的非关键描述不必逐字结构化；会改变世界或被后续依赖的细节必须进入事件。

### 6.4 提交与因果

每次任务捕获：隐私 epoch、worldId、lifeEpoch、人格／生活设定版本、计划版本、状态修订与来源修订。

模型调用结束后，在短事务中重新检查这些值及活动的当前状态，然后一次提交：

1. 幂等事件记录；
2. 状态效果与新状态修订；
3. 最小角色记忆；
4. 活动推进／任务完成游标；
5. 供前端同步的公开更新事件。

版本不符则丢弃候选，必要时用同一活动身份重新排队。不得只推进游标而没有事件，也不得先删除旧记忆再异步创建新记忆。

### 6.5 每日收尾

收尾压缩普通活动，提取值得延续的结果与未完事项。第二天在这些状态上排程，不重新随机开局。情绪余韵可以按时间衰减；衰减基于经过时间，不基于 tick 或聊天次数。

## 7. 与聊天连接

### 7.1 前台读取

`executeRun` 在构建上下文前捕获本轮生活开关与世界版本。生活关闭时执行原上下文路径，不增加生活查询和提示词。

开启时，LifeService 先做有界、无模型的边界核对：提交可确定的简单变化，安排需要模型的结算任务。随后读出快照，不能让一次普通聊天等待生活模型调用。

若某项活动尚未结算，快照明确标注 planned／in_progress／pending_resolution 和 asOf。聊天只能按已有状态表达，例如「本来准备下午试试」，不能自行补成已完成故事。

### 7.2 上下文分区

新增独立结构化生活块：

- 当前世界和生活设定版本；
- 当前活动、已确认的状态及快照时间；
- 今天已经发生的少量事件；
- 与当前话题相关的角色记忆；
- 少量未完目标；
- 用户明确询问未来安排时才提供相应计划。

该块与用户事实、现实约定、聊天历史分别标明语义和来源。初始预算建议不超过 1200 tokens，在总上下文预算内分配，优先保留当前用户输入和既有明确边界。

召回组合为相关性、近期性、重要度、因果关联和重复提及惩罚。先用 SQLite 及关键词／FTS；第一版不以向量检索为前置依赖。

人物说话可根据当前生活自然变化，但不能每次回复都汇报日程。没有相关经历时可以正常回应或说明尚未决定。回答语气继续由 Persona 控制。

### 7.3 用户影响未来

后续增加窄工具 `propose_life_change`，只允许处理未发生安排或已登记目标。程序根据当前用户输入验证授权和目标身份；模糊建议可以留为候选，明确的世界内调整可直接提交，不需要逐条日常审批。

「我今晚加班」是用户事实，不自动改变角色职业或工作时间；「你今晚先别看那部电影，明天我们一起聊」才可能调整她的计划。

「一起聊过电影」可基于聊天证据写为共同互动；「一起看完电影」需要更明确的参与与完成证据。邀请、同意、参与、完成分别表达。

### 7.4 对话中出现新经历

普通聊天不能绕过 LifeService 静默创建重大过去。模型可以自然补充不改变既有事件含义的表达细节；新的稳定事实、状态变化或共同经历必须有领域记录或用户证据。

如果出现矛盾，通过更正或未来计划调整解决。引用 eventId 是可追溯措施，不是语义正确的数学证明；要用场景评测检查模型是否仍在编造未记录事件，不能承诺零幻觉。

## 8. 后台执行与资源预算

复用 Harness 的前台／后台互斥。LifeService 不启动另一个定时器循环；`tick` 在生活开启时选择一个到期 LifeJob。

建议优先级：当前用户对话与取消 → 明确到期约定 → 当前生活必要结算 → 用户记忆提取／整理 → 可选计划变化、故事、主动分享。通过任务年龄和配额避免低优先级任务永久饥饿。

用户输入打断生活模型调用时，任务保留输入版本并退回待处理；源已失效的任务取消。下一次空闲重新校验，不能无脑重跑旧快照。进程内继续维持每 bot 一个后台模型请求；多 bot 受进程级并发上限约束。

首版预算参数是待校准的起点：

- 每天至多一次模型参与的初始计划，其余以 routine 为基础；
- 每天至多两次值得展开的事件结算；
- 每天至多一次语言整理；
- 每项调用约 25 秒截止时间，最多一次可安全重试／修复，尝试计入配额；
- 普通工作单合计至多四项；包含失败、重试和修复的实际模型请求总上限先设为六次，达到任一调用或 token 上限即降级，不为凑满工作单突破配额；
- 生活 token 额度不超过当前 bot 总日额度的 10%，并设置单独上限，例如 8000 tokens；受总额度优先约束。

这些是调用与费用上界配置，不是“每天必须发生两件趣事”。预算不足、模型失败时继续使用可确定的基础状态，对尚未确定的结果保持未结算。

一日自然边界、活动边界和用户明确调整触发工作；不每分钟调用模型。具体调用次数和成本在 Trace／用量中按 `life_plan`、`life_resolve`、`life_reflect` 分开记录，不在方案阶段估算未经验证的人民币费用。

## 9. 开关和版本语义

| 设置 | 默认 | 依赖 | 关闭的行为 |
|---|---|---|---|
| `characterLifeEnabled` 角色日常 | false | 有已发布生活设定才能启动 | 立即取消自主生活任务和主动分享；本轮普通对话使用已捕获快照，下一轮不再注入生活 |
| `storyArcsEnabled` 跨天故事 | false | 角色日常 | 冻结剧情编排，基础作息、个人记忆和普通未完事项继续 |
| `lifeSharingEnabled` 主动分享日常 | false | 角色日常及现有主动联系许可 | 取消尚未发布的自主分享，保留已发消息 |
| 现有 `splitReplies` / `messagePacing` | 保留当前设置 | 既有依赖 | 沿用已实现的下一轮生效规则 |

角色记忆与 routine 是角色日常的基础机制，不单独提供容易造成失忆或无作息的开关。首版不用“角色有日常但不保存任何经历”的不一致模式。

依赖未满足的子选项不生效，界面显示原因；不得偷偷开启父功能。可以保留子选项的用户选择，通过 effective 状态表达当前是否有效。

暂停不会删除历史。重新开启从当前日期续接，暂停期间不合成一串“她一直在生活”的事件。已经开始的活动以暂停处理，不因恢复而声称持续做了数天。重新启用不会重发暂停前的过期分享。

已经聊过的生活内容仍是聊天历史的一部分；关闭功能不等于回滚到试用前。要完全移除这些经历，应使用明确的遗忘／重置操作，并按依赖清理。

发布新生活设定只重排未来；已发生事件保留原设定版本。发生根本世界变更时提供显式“新生活版本／重置世界”，不自动清空旧世界。删除或遗忘是单独操作。

新角色和旧角色缺少配置时均保持关闭。功能开关是持久用户配置，不依赖浏览器 localStorage。

## 10. 时间、离线与恢复

世界时钟默认使用角色设置中的 IANA 时区，以真实时间 1:1 推进，不随聊天轮数加速。UTC 保存发生时间，保留当地日期／时区和排程规则。跨午夜和 DST 继续使用 Temporal，不能用固定 24 小时代表所有当地自然日。

时区修改只影响未来排程；历史事件的时间和原时区保留。时钟回拨不回滚已提交事件，也不重复活动；推进游标与幂等身份共同防止重复，明显时钟异常标记为待对齐。

区别三种情况：

1. **页面关闭、后台仍在**：正常推进；通知是否触达仍受现有浏览器通道限制。
2. **功能开启但进程离线**：允许有界重建独处生活；保存离线重建标记，先衔接当前状态。长时间离线只生成有限摘要，不逐日、逐分钟补演，不补发过期消息。
3. **用户明确关闭／归档**：世界暂停，恢复时不追演暂停期间。

离线补齐建议最多展开最近一天，较早缺口最多用一次有界摘要衔接；重建预算包含在当天生活额度中。涉及用户的待参加活动保持等待／过期，不能离线替用户完成。尚未确定的关键结果可以继续未知。

内容生成任务恢复后可在新鲜度检查通过时重新排队；已经提交的事件不会再次结算。主动消息的发送恢复另按 Outbox 合同处理，不能把恢复历史等同于重新发送。

## 11. 主动分享的后续接入

事件提交后可以产生分享候选，候选具有 eventId、相关记忆、动机、时间窗、主题去重键和来源版本。候选存在不代表必须发送。

决策顺序：

1. 检查日常／分享开关、主动许可、免打扰、静默时间、预算与来源；
2. 检查近期是否已经说过、用户是否正在交谈、是否持续未回复；
3. 判断这个经历是否值得现在分享；
4. 生成一次有界表达，交给消息组发布器；
5. 每条发布前重新检查取消和时效，用户插话立即停止余下内容。

不借用未经确认的用户 FollowUp 绕过旧规则。独立 LifeShareIntent 是角色自主表达来源；其权限来自角色生活／主动分享配置。

这里有真实的现有合同改造：当前 `Run.inputId`、`executeRun` 假设输入是用户 Message，Delivery 假设有 FollowUp。新增主动分享时需要明确区分用户输入和生活来源，并迁移依赖这些假设的查询、历史和回执。

建议增加兼容旧记录的 Run origin：`user`／`life_share`；旧记录按 user 解释。生活 Run 不创建伪造的用户消息，使用独立执行入口和已有预算／取消边界。分条发布器提取为可共用的 MessagePublisher，仍按已发布消息持久化。

主动 Run 分配稳定入队序号，消息进入主聊天历史。上下文支持连续的助手消息，不能假设历史永远是用户／助手交替。未发布草稿仍不进入快照或对话历史。

Delivery 扩展可区分 followup／life_share 来源；旧 followUpId 路径保持兼容，新来源检查自己的授权与有效性。浏览器通知仅引用已发布首条消息，一组表达默认最多一个提醒。离线生成保留站内消息，不在回来后补弹过期提醒。

主动额度按“一次接触／消息组”计算，不按气泡或 Notification API 调用次数计算。多个 bot 还需 BotManager 层的 owner 级统一准入：发送前统计所有角色近期已发布接触，同一同步临界段内完成最终准入和首条提交；归档角色近期记录仍需纳入。单进程阶段可由持久接触记录重建统计，避免为此先引入分布式服务。

这项自发联系额度针对自主分享和非承诺关心；用户明确建立的提醒继续遵守原约定策略，不因新功能消耗额度而被静默吞掉。既有主动许可与静默规则仍统一检查。

## 12. 遗忘、更正、导出与迁移

### 12.1 来源链

生活引用采用带类型的 LifeSourceRef，支持已发布设定、计划、事件、用户消息及可选外部事实。携带实际作用域、worldId、ID 和修订，不能只有一段来源文字。

用户来源被遗忘时，相关计划、事件派生部分、记忆、任务、分享候选和状态投影失效；独立的其他角色活动可保留。第一版可扫描当前 bot 的有限数据并重建状态，不引入来源图数据库。

### 12.2 删除清单与恢复

现有删除清单需要向后兼容地扩展 lifeEventIds、lifeMemoryIds、lifeWorldIds；`restoreBackup` 的清单合并与 `Store.applyLedger` 必须认识新字段。恢复时先迁移，再应用清单，之后才允许 LifeService 读取或排程。

删除保留不含正文的去重身份，清除正文、派生摘要、索引、相关 Trace、快照缓存及旧导出；旧备份恢复也不能复活。来源失效时同时增加隐私 epoch 与 lifeEpoch，使在途模型候选不能重写回来。

生活快照来源记录进入 Run 上下文元信息。涉及已遗忘事件的助手消息按依赖关系清理，避免正文仍保留已删除的生活细节；普通关闭开关不执行这种清理。

界面区分「移除整理条目，保留经历」与「遗忘这段经历」。前者保留事件，角色仍可引用该经历，同时为被移除投影保留不自动重建的标记；后者清除事件及依赖记忆和表达，不能仅隐藏一个摘要就声称已经遗忘。

### 12.3 数据版本

当前代码只接受 SQLite user_version ≤ 1。首次生活系统 migration 升到 2，并在事务中创建生活表和索引；旧二进制必须继续拒绝读取新 schema，不能把版本号强改回去来回滚。

升级前保留一致性备份。旧角色的开关缺省为 false，不自动填充生活设定和历史。失败迁移回滚；回滚程序时使用迁移前备份，不能把丢弃新数据当成无损降级。

SQLite 备份自然包含生活表，JSON 导出需要显式新增独立 characterLife 命名空间和版本。生活记忆不能导出成用户事实。BYOK 凭据继续沿用现有隔离，不进入导出和数据库备份。

## 13. UI 与接口

### UI

当前角色增加「生活」页，主要呈现：生活开关、设定草稿／发布状态、routine、今天的计划、已发生事件、角色记忆。计划与经历用文字状态明确区分，未来剧情不默认完整展示。

聊天保持原入口。用户可以问「今天做了什么」「下午准备干吗」，无需进入调试界面。生活面板用于理解和调整角色，不要求用户手动维护所有活动。

第一版只展示角色日常主开关；故事和主动分享完成后分别上线，不提前放置无法工作的开关。

### 拟新增 API

全部沿用当前认证、CSRF、bot 选择与作用域校验；写入要求 expectedRevision。

| 方法 | 路径 | 行为 |
|---|---|---|
| GET | `/v1/character-life/profile` | 当前发布设定及版本 |
| POST | `/v1/character-life/profile-drafts` | 显式生成／保存一次草稿，有幂等键和预算 |
| POST | `/v1/character-life/profile-publish` | 校验并发布，不自动开启生活 |
| PATCH | 现有 settings 路径 | 设置当前 bot 的开关 |
| GET | `/v1/character-life/snapshot` | 已提交当前状态、asOf、版本和准备状态 |
| GET | `/v1/character-life/days/:date` | 分开的当天计划与经历，查询不调用模型 |
| GET | `/v1/character-life/memories` | 本角色记忆的有界检索 |
| POST | `/v1/character-life/plan-adjustments` | 调整尚未发生的活动 |
| POST | `/v1/character-life/event-corrections` | 有版本的事件更正 |
| POST | `/v1/character-life/forget` | 持久记录遗忘并传播失效 |

前端事件先用 `life.profile_published`、`life.plan_updated`、`life.event_committed`、`life.paused`、`life.invalidated`。事件只用于通知客户端读取新状态，不充当模型记忆或权威事件正文来源。

## 14. 验证与验收

先建立固定时钟、模型替身及三天／三十天虚拟时间夹具。程序正确性测试与真实模型内容评测分开报告。

| 场景 | 必须观察到的结果 |
|---|---|
| 全部关闭 | 原聊天上下文不增加生活块，生活调用／排程为零 |
| 两个角色 | 设定、routine、事件、记忆、开关和任务互不串用 |
| 再次查询今天 | 已发生事件 ID 和结果不变，不产生新世界版本 |
| 重复 tick／跨日 | 一个活动仅结算一次，未完状态进入次日 |
| 计划进行中 | 能区分“准备／正在／已经”，不提前生成完成回忆 |
| 时间约束 | 不重叠、通勤可行、跨夜和 DST 按既定规则处理 |
| 用户调整计划 | 仅未来活动变化，既有事件保持原样 |
| 共同活动 | 邀请未同意、同意未参加、参与未完成分别表达 |
| 人格／设定更新 | 旧后台结果不提交，新版本只影响未来 |
| 关闭／归档 | 任务停止、分享失效，恢复不补演暂停期 |
| 模型不响应取消 | 迟到候选不能提交，前台聊天可以继续 |
| 事务提交前后崩溃 | 事件、记忆、状态与游标不出现半提交 |
| 进程离线数天 | 有界重建，用户参与不被代办，过期私信不补发 |
| 遗忘／旧备份恢复 | 所有依赖失效，已删内容不复活 |
| 主动分享阶段 | 入主聊天，插话／停止取消尾段，刷新不重发 |
| 多 bot 主动联系 | 单角色与 owner 总额度均成立 |

内容质量评测另用相同设定运行至少连续三天，加入十到二十个追问／干预场景，例如追问早餐、临时约电影、取消安排、第二天问上次的结果。人工评估身份一致、因果连续、普通生活比例、个性差异与表达自然度。固定测试通过不能宣称真实模型永不矛盾。

实施阶段按改动运行 typecheck、相关单测、完整回归、浏览器场景和真实进程故障检查。所有付费模型评测显式区分，测试替身结果不当作真人感证明。本轮设计没有运行新功能测试，也未声称已经验收。

## 15. 分阶段交付

| 阶段 | 交付 | 阶段结束标准 |
|---|---|---|
| L1 设定与存储 | 六表 migration、默认关闭、设定草稿与发布、routine 编译、生活页基础 | 旧数据与聊天保持兼容，可配置一个角色的可行生活 |
| L2 一天与记忆闭环 | DayPlan、活动推进、事件、状态／记忆、预算与取消、聊天投影、遗忘恢复 | 固定时钟连续三天可重复，用户追问前后一致 |
| L3 互动与生活质量 | 对话调整未来安排、有限个性化活动、离线重建、三十天重复性检查 | 用户建议有后果，普通日子和变化自然共存 |
| L4 主动分享 | 独立开关、ShareIntent、主动 Run／Delivery 合同、主聊天与消息组、owner 准入 | 有理由才联系，插话／停止／刷新／重启均符合发送合同 |
| L5 可选故事编排 | 独立故事开关、少量 arc／beat、参与证据与用户影响 | 主题线有因果，关闭故事仍能正常生活 |

L1 和 L2 共同构成第一个可使用版本，不能只交付一张日程表就称为“角色有了生活”。先以一个配置完整的角色做三天演练，通过后再为其他角色分别发布设定；不批量改变现有 bot。

## 16. 参考与适配决定

开源产品机制沿用[已有固定版本调研](../research/story-and-proactive-messaging.md)和[source lock](../research/story-system-source-lock.json)：Yuralume 的日程／经历／余韵、Generative Agents 的记忆与规划、AIRI／OpenClaw 的运行与投递边界。此方案不声称重新验证当前上游，也不引入这些完整后端。

本轮使用 `engineer-agents-with-kimi` 技能检查持久记录和恢复边界。重新核对固定快照声明、`wire/wireService.ts` 及 `test/wire/resume.test.ts`，Kimi commit 为 `9e1248416faa22d9f0b777b91ad092bbf1e19182`，快照日期 2026-07-19。

| 目标需求 | 提炼原则 | 决定 | 最小适配与验证 |
|---|---|---|---|
| 角色经历跨天保留 | 持久事实与上下文投影分开 | Adapt | LifeEvent 权威、状态／记忆可重建；检验删除与重建 |
| 后台推进与对话互不覆盖 | 状态归属于拥有它的身份与版本 | Adapt | 复用每 bot Harness、作用域与提交栅栏；检验跨 bot 和旧结果 |
| 重启不会重复发生／发送 | 恢复记录不重新执行副作用 | Adapt | 内容任务可重排但先查幂等事件；发送另走 Outbox；检验提交前后崩溃 |
| 小型陪伴运行时 | 仅引入当下需要的机制 | Defer | 不引入 Kimi DI、wire 格式、多 Agent、持续内心独白或分布式租约 |

项目目录当前无 Git 元数据。本方案以本次读取的实际源码为基线；旧冻结文档里的“未实现”及旧测试数字不作为当前新功能状态。新增类型、文件与接口均为拟议设计，后续实现必须记录实际差异。
