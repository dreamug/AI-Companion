当前完整自用阶段仍为 M0–M5。未来产品化使用 W1–W3 阶段，详见[网页与规模演进](web-and-scaling-roadmap.md)。十万注册、十万日活、十万同时生成分别建模；没有现成容量承诺。

M0正式接口只有输入、取消、快照、SSE、状态开关与通知attempt／回执；其余必要管理动作使用一个本地维护表单和受保护入口。允许手工操作，不允许绕过领域修订与删除检查直接写数据库。完整runner、工具循环与canary自动化分阶段加入。

## 2. 为什么选 TS，而不是现在改为 Python

网页前端不决定后端语言。选择 TS 的项目依据是：首版以远程模型调用、事件流、数据库访问和任务编排为主；没有已确定必须在 Harness 进程内执行的 Python 模型；未来网页可以复用部分协议类型与校验定义，单人维护时少一套语言边界。

这是工程权衡，不是 TS 在人格、记忆或推理质量上天然优于 Python。Python＋异步 Web 服务也能实现同样合同；“使用模型 SDK”和“自研 Harness”也不是二选一。双方都应复用成熟的数据库、网络和协议库。

不因未来可能有十万用户而改语言。Node.js 的异步 I/O 与多实例部署提供可扩展基础，但阻塞计算、慢查询、长连接资源和提供方配额仍需治理。[Node.js 事件循环](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)、[多进程机制](https://nodejs.org/api/cluster.html)

重新评估条件：已确定的 Python 组件带来可复现的质量收益；主要维护者的 Python 积累明显改变交付成本；或性能剖析证明某个计算模块需要另一运行时。优先隔离该组件为 Worker／服务，不据此重写全部人格、记忆和关心领域。

## 3. AI SDK 的准确位置

AI SDK 是模型开发工具包。其 Core 提供模型生成、结构化结果与工具调用等能力；这些能力是基础设施。我们不采用其 UI 或完整 Harness 抽象作为当前产品内核。[官方介绍](https://ai-sdk.dev/docs/introduction)

| 自有模块 | 掌握的权力 | AI SDK 参与范围 |
|---|---|---|
| Persona／Safety Policy | 发布权限、有效版本、关系边界 | 接收已投影的上下文 |
| Memory | 来源、有效期、修订、遗忘、召回选择 | 为提取或归纳提供一次模型调用 |
| Concern Policy／Scheduler | 候选资格、时间窗、频率、取消 | 为判断和草稿生成提供模型调用 |
| Run Controller | 排队、Step、截止时间、预算、取消、终态 | 执行一次受控模型请求 |
| Tool Executor | 参数、授权、事务、副作用回执 | 解析并返回模型提出的工具请求 |
| Model Gateway | 规范化请求、错误、usage、适配选择 | 提供方通信、流式解析与协议映射 |
| Delivery／Outbox | 投递资格、尝试状态与回执 | 不参与外部消息发送 |

默认按“一次模型 Step”调用 SDK。工具参数完整后由我们的执行器验证和执行，再决定是否续步；不把带副作用的领域工具交给未经控制的自动 `execute` 回调。即使借用 SDK 的停止或工具辅助能力，也不能再启动一个独立于 Harness 的重试、预算或续跑循环。[工具调用文档](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling)

## 4. 必须可替换的边界

1. 领域消息、工具请求、公开事件和模型历史采用我们自己的版本化 Schema，不把 SDK 对象写成权威存储。
2. 只有模型适配器导入 AI SDK／DeepSeek Provider 类型；领域通过 Model Gateway 调用。静态 Schema 校验库不等于模型 SDK，可以由合同层复用。
3. SDK 默认重试关闭；重试资格由 Gateway 判定，次数／耗时／费用计入所属 Run 或 Job。
4. 原始流先规范化；持久化并授权后发布应用事件。客户端不依赖供应方或 SDK 的原始流格式。
5. 提供方能力显式声明并验证，不能假设统一接口消除了工具、JSON、取消、缓存或 usage 差异。

切换适配器的验收是：同一套领域场景仍成立，只允许已声明的提供方能力差异；不承诺所有模型的体验或参数完全等价。[接口与运行合同](api-and-runtime-contracts.md)定义可观察结果。

## 5. 自用简化与未来规模的界线

首版不实现账号系统、分布式租约、Redis、微服务或数据库集群。首版即保留 ownerUserId、relationshipId、可替换存储、幂等键和版本检查，避免以后把全局单例当成所有用户共享的身份。

未来并发约束按关系实例生效：同一用户与角色的一段关系最多一个面向用户的生成 Run；不同关系可以并行。角色模板可以共享，个人记忆、边界、工作状态、配额和投递不能共享。

当前“Local-first”描述自用部署；未来托管网页必须另做数据存放、账号权限、隐私、通知和运维方案，不能继续声称所有数据仅在个人电脑上。

## 6. 已采用、调整与后置的工程经验

目标需要：长期事实不能被某个 SDK 消息格式或当前上下文窗口绑死；状态归属于用户关系，Run 只是临时投影。

固定证据：Kimi 快照 `9e1248416faa22d9f0b777b91ad092bbf1e19182` 中的 contextProjector 实现与 tool-exchanges 测试，见[证据 K1–K3](../research/source-evidence.md#kimi-固定快照补充证据)。本轮复查了投影实现及测试，没有执行它们。

提炼原则：持久事实与模型投影分开，协议修复必须可观察。决定为 Adopt 原则、Adapt 投影；最小落点是自有消息与 Step 记录＋模型适配器映射。验证为完整工具交换、取消、断线恢复与替换模型端口的合同测试。Kimi 的 DI、Scope 和通用服务布局不复制。
