# 开源实现比较与技术选型建议

v0.3 · 2026-10-23 · 冻结。认知状态：本文为固定源码观察与适配判断，未部署或执行上游测试；数字不是容量结果。M0期间只登记[实现偏差](../engineering/implementation-notes.md)，冲突按[权威规则](../../README.md#文档冻结与权威规则)处理，固定源码观察不随选型改写。

选型：TS自研Harness与有界执行器，AI SDK Core仅为可替换模型接入；后续本地Web／Electron再到App。首周用Trace常驻页浏览器Notification，不接外部IM；必要时极薄Electron托盘只作投递适配。Letta只阅读，AIRI有明确收益才最多试接2人日。见[评审回应](../engineering/review-response.md)与[技术决策](../engineering/architecture-decisions.md)。

## 1. 建议结论

默认选择：**独立的 TypeScript 无界面 Harness，直接复用模型 SDK、数据库、Schema 校验和测试工具；自己掌握人格权限、事实记忆、关系约定、主动关心与投递状态。**

主要参考组合：

- SillyTavern／RisuAI／Agnai：人格与上下文编排、记忆预算、来源与聊天变更的关联。
- Letta：持久身份、已提交记忆投影、记忆约束、后台整理。
- AIRI：无界面运行端口、事件型通知、取消与会话身份、未来桌面及语音交互。
- Memobase／Mem0／Graphiti／Hindsight／MemOS／EverOS：画像、时间、来源、更新、归纳、纠错与索引一致性。
- OpenClaw：调度、运行准入、发送前再次检查、重启与投递状态。
- Open-LLM-VTuber／Pipecat：实际听到的内容、打断、语音轮次和资源清理。
- Kimi：记录与上下文投影的边界、有界运行和故障语义；只参考固定快照。

**当前不建议Fork某个完整应用作为主项目。** AIRI的`core-agent`和Letta本地Headless Backend均有可参考边界；不安排Letta接入，AIRI也不是默认前置实验。二者不能直接当完整陪伴内核。判断来自依赖和职责分析，不来自运行性能比较。

现成记忆引擎保持为可替换的候选和基线。默认版本先用小而明确的领域模型实现闭环，不自行重写模型协议、数据库、向量数据库或语音引擎。

首周不要求部署Mem0／Hindsight。先积累真实保留样本，当前记忆基线出现具体不足时只选一个外部引擎对照，避免再增加两项前置实验。

网页产品不决定后端语言；当前选择TS基于远程模型编排和维护成本，并非对Python能力作否定。未来十万级用户的存储、任务与部署演进见[规模路线](../engineering/web-and-scaling-roadmap.md)。本报告的单用户适配判断不构成上游或本产品的多用户容量证明。

## 2. 证据强度与研究边界

原调研固定了14个开源相关项目、2个底层库，以及1个另行分类的源码可见桌面感知项目的Commit，缓存181个源码、配置、测试及说明文件；当时缓存全部通过Git blob校验。重点检查四个产品能力及运行边界，**没有逐行审计全部缓存文件，更没有审计所有仓库文件**。v0.3沿用该固定证据，没有重新抓取全部上游。

另检查 Kimi 本地固定快照 `9e1248416faa22d9f0b777b91ad092bbf1e19182`，日期为 2026-07-19，没有把它与当前上游行为混在一起。

调研完成的是静态实现与测试阅读。迄今没有安装项目、运行上游测试、调用付费模型或进行用户体验测试。以下使用三类表述：

- **实现观察**：具体路径中确实存在的行为。
- **适配判断**：根据我们的身份、时效、持久化和交互要求得出的选择。
- **待验证**：需要后续适配实验或真实使用才能证明的事情。

完整出处见 [源码证据索引](source-evidence.md)，标识如 A1、L2、H3 对应固定版本链接。

## 3. 对前期材料的修正

1. AIRI 不能再简单描述为“运行逻辑都在前端”。它已经有平台中立的 `core-agent`，包含会话端口、流式轮次、通知 Agent 和测试。另一方面，该包仍是内部 workspace 包，记忆与部分调度宿主仍在界面 store 中。两件事必须同时成立。[A1–A8]
2. AIRI 的长期记忆并非完全没有实现。当前检查到的是按角色作用域管理的条目索引与读写工具；它尚不能直接替代本产品对来源、有效时间、纠错和遗忘传播的要求。[A5]
3. Letta Code 有实际本地执行 Backend，并非只能依赖旧版 API 服务。其记忆有 Git 提交投影、容量限制和只读路径保护，不能笼统归类为“允许无限自主改人格”。[L1–L5]
4. Open-LLM-VTuber 的“主动发言”确实有服务端触发入口，但触发输入跳过记忆／历史，不等于已经实现长期关心的候选、时效和闭环状态。[V2]
5. Graphiti 的时间不是一个普通 timestamp。事实成立时间、失效时间、系统过期与来源分别表达，尤其要区分“承诺未来发生”与“已经发生”。[T1–T3]
6. 永久保存聊天、摘要和用户长期记忆，分别承担不同职责。清空当前上下文、隐藏过期条目、真正遗忘，也必须有不同的语义。[ST3–ST4、M3、K3]

## 4. 核心项目逐项比较

下面比较固定版本中已检查的路径，不做未经实测的星级排名。单项存在不代表完整产品能力已达标。

| 项目 | 人格 | 长期记忆 | 主动关心相关实现 | 桌面陪伴 | 无界面底座适配 |
|---|---|---|---|---|---|
| SillyTavern | 角色与提示词编排 | 消息摘要、动态知识／向量召回 | 本轮检查路径不足以替代持久关心策略 | 主要为聊天应用 | 去界面耦合成本较高 |
| RisuAI | 角色配置与提示控制 | 分层摘要选择、来源 memo 关联 | 本轮重点不在持久主动调度 | 跨平台聊天与角色呈现 | 记忆算法依赖应用数据结构 |
| Agnai | Persona 与聊天 Prompt | 记忆书、预算和激活 | 仍需自有时间与关心域 | 网页服务 | 单用户阶段带入多余服务职责 |
| AIRI | 角色卡与会话身份 | 条目索引与工具；完整领域需补充 | 独立 Spark Notify＋Stage 任务调度 | 角色、语音、电源事件等 | 已有 core-agent；内部依赖需验证 |
| Letta Code | 人格记忆与版本投影 | MemFS、核心／延后记忆与约束 | 通用后台能力，仍需陪伴语义 | 多入口，非本轮桌面外壳候选 | 本地 Headless Backend 确实存在 |
| Open-LLM-VTuber | 系统人格配置 | 基础历史恢复与可替换 Agent | 主动发言信号，未等同关心闭环 | 语音、Live2D、桌面交互 | 与语音／WebSocket 宿主相连 |
| 专用记忆项目 | 通常不负责人格发布权限 | 画像、事实、归纳或时间图 | 可供候选来源，不独占发送决策 | 通常不负责 | 适合用端口接入与对照 |
| OpenClaw | 通用 Agent 身份／Prompt | 通用记忆扩展 | 持久调度、投递栅栏与恢复 | 多渠道运行 | 完整宿主过大，借鉴必要合同 |
| Pipecat | 不承担本产品人格域 | 不替代事实记忆 | 不承担关心领域 | 实时语音与轮次 | 未来作为输入输出适配器 |

### 4.1 SillyTavern

**实际实现。** `PromptManager.js` 使用角色、扩展提示和界面配置，同时直接依赖主应用、DOM 与模板。World Info 提供动态激活、预算及 sticky／cooldown。摘要扩展把结果挂在聊天消息的 `extra.memory` 上，生成后会检查会话身份是否变化。[ST1–ST4]

**值得借鉴。** 把人格、示例、知识、摘要与近期聊天分开，并能够解释哪些块被放进了模型上下文；摘要必须知道基于哪段历史生成。

**适配限制。** 这些模块并非独立的服务端 SDK。聊天轮次激活机制也不能直接替代现实时间调度。若移除前端，还要接管大量应用状态。

**决定。** 借鉴设计与配置语义；保留为角色对话体验基线。当前不直接复制其提示词管理器或 Fork 整个应用。源码为 AGPL 系列，研究机制与复制代码在工程上分开处理。

### 4.2 RisuAI

**实际实现。** HypaMemory V3 在预算中分别选择重要、近期、相似和可选随机摘要；摘要保留源聊天 memo 集合，源聊天删除后清理失去完整来源的摘要。[R1–R3]

**值得借鉴。** 长期记忆选择要保留不同信息的配额；来源变化会影响衍生摘要。缓存也应包含上下文身份，不能只按文本相同就复用结果。

**适配限制。** 实现依赖自身聊天数据、Tokenizer、模型调用与应用存储。随机回忆会降低回归可重复性；其趣味价值需要独立体验实验。

**决定。** 借鉴预算与来源失效；默认不采用随机记忆注入。不把这套压缩算法直接当成事实数据库。GPL 代码暂不纳入产品依赖。

### 4.3 Agnai

**实际实现。** Memory Book 在给定扫描范围内触发条目，按 priority 选择预算内内容，再根据 weight 等规则排列；有针对触发、预算和顺序的测试。[G1–G2]

**值得借鉴。** “是否进入上下文”和“进入后放在哪里”是不同决策；所有淘汰都应可解释。

**适配限制。** Memory Book 是上下文激活机制；多用户服务和角色平台会带来我们当前不需要的职责。

**决定。** 借鉴选择／排序分离与测试方法。第一版不以其 SaaS 应用为基础。

### 4.4 AIRI

**实际实现。** `core-agent` 通过宿主端口接收会话、上下文与模型能力；有持久用户提交确认、队列身份、会话代数、取消和部分输出测试。Spark Notify 允许不响应。Stage 中长期记忆当前使用 localStorage 条目索引；Notebook 和一条任务调度路径仍在 Pinia store 中，使用 leader 检查与定时器。[A1–A8]

**值得直接考虑的部分。** 平台中立的消息投影、流式边界、取消策略和测试。MIT 许可使小模块抽取成为可行候选。未来桌面角色与声音表现，也应先评估它而非重写。

**适配限制。** `@proj-airi/core-agent` 标记为 private，依赖 provider-inference、stream-kit、协议、音频等多个 workspace 包。接口中用户提交有异步持久确认，助手追加仍由宿主提供；接入后仍要设计我们自己的事务、Outbox 和失败恢复。通知决策模块不承担完整持久调度。

**决定。** 它是最值得保留的无界面复用候选，暂不成为生产硬依赖。默认不做接入实验；只有出现可明确节省的缺口，才用最多2人日（12小时有效开发）验证，且不阻塞真实原型。若后续实验满足无Stage UI、依赖可控与消息／提交合同，可提供执行辅助适配；运行准入、权限、预算、取消和领域提交仍由自有Harness掌握，不引入第二个不受控循环。

**不作的推断。** 所检查的 store 未见某字段，不能证明全仓所有分支都不支持；上述判断只针对固定版本与明确路径。

### 4.5 Letta Code

**实际实现。** 人格可以映射到记忆文件；切换人格前检查未提交改动，并创建提交。本地系统提示词按已提交 Git 版本编译。约束支持核心总量、单文件大小、目录深度与只读文件；本地执行器具备确定性测试模式与真实模型适配。[L1–L5]

**值得借鉴。** 记忆修改有版本，生效版本可追溯；人格核心与可写记忆可以设不同权限。将记忆整理与前台交流分工。

**适配限制。** 需要对齐其 agent、conversation、工具执行与 MemFS 生命周期；代码助手与通用 Agent 的自主文件操作，不是我们第一版的必要能力。采用它的本地 backend 也不自动获得陪伴域的约定、关注事项和投递事务。

**决定。** 降为源码设计参考，不安排执行器接入实验；借鉴提交投影、约束和确定性测试。其本地 Backend 是 TypeScript，降级不是因为必然引入 Python。不直接复制它的 Git／工作树同步层，不把可修改文件当成我们的第一版权威事实存储。

### 4.6 Open-LLM-VTuber

**实际实现。** 基础 Memory Agent 用内存消息列表并从历史恢复；中断时把历史修正为实际听到的助手文本。主动发言入口收到信号后构造提示，触发输入标记跳过记忆和历史。[V1–V2]

**值得借鉴。** 生成了多少、显示了多少、播放了多少，不能混为一谈。人格输出和语音表现需要统一身份，但传输状态必须独立。

**适配限制。** 当前 Python 后端与语音、WebSocket、角色配置交织。直接扩展仍需重做本产品的事实记忆和关心策略。项目源码与样例模型许可分开。[V3]

**决定。** 后续桌面／语音交互参考，不作为当前无界面 Harness 底座。不能因为看到 `mem0_llm.py` 或 `letta_agent.py` 文件，就推断适配已完整支持当前版本 API。

## 5. 长期记忆引擎的取舍

| 项目 | 实现中最有用的机制 | 本产品的使用方式 | 当前不整套引入的原因 |
|---|---|---|---|
| Memobase | 画像主题、严格模式、事件摘要、后台 buffer | 借鉴画像范围与批量整理；作为外部记忆基线 | Python＋数据库＋Redis 的服务形态；领域事务仍需自己掌握 |
| Mem0 | TS/Python OSS、CRUD、历史、作用域、过期过滤 | 优先的轻量外部记忆候选；通过端口做同题对照 | 自由文本记忆不能自动成为已确认偏好／约定；还需来源与更正传播 |
| Graphiti | 来源、双时间语义、事实失效、图检索 | 借鉴时间与来源字段；复杂关联明确出现后再考虑图 | 当前一个人、一个角色，无需先承担图服务与抽取成本 |
| Hindsight | retain／归纳分工、来源依赖、批量事务、删除并发测试 | 质量优先的服务型记忆对照候选；借鉴事务与源存活重检 | 完整运行时和存储较重；仍需验证中文陪伴与本地维护代价 |
| MemOS | 反馈证据、修复冷却、异步上下文、可检查记忆 | 借鉴反馈形成修订建议的流程 | 本地插件的宿主适配、经验／技能体系超出当前范围 |
| EverOS | 本地可读文件、索引同步、变更与删除对账 | 借鉴可导出性、索引可重建、一致性验收 | 同时维护文件权威源和索引会新增一致性职责 |

依据分别是 B1–B3、M1–M3、T1–T3、H1–H4、O1–O2、E1–E2。

两个关键工程教训：

1. **记忆归纳的结果和进度必须一起提交。** Hindsight 的回归用例表明，在“删除旧结论＋创建新结论”之间失败会造成数据损失；只推进归纳游标也会造成永久漏处理。[H3]
2. **写入前再次确认来源仍有效。** 模型提取期间用户可能已经删除或纠正源信息，旧后台结果不能把它重新写回来。[H2、H4]

个人版默认由SQLite保存权威事实、版本、来源与归纳游标；关键词／向量索引是可重建投影。未来托管多用户迁移PostgreSQL，保持相同来源与提交合同。记忆引擎通过适配器提供候选证据，不能绕过权威状态检查改写人格、边界和承诺。

## 6. 主动关心：参考 OpenClaw，自己定义关心领域

OpenClaw 实现有投递前栅栏：重查 owner、运行代数、取消状态，开始投递前记下尝试；相关测试覆盖重启、中断和状态保持。[C1–C3]

采用的原则：

- 调度发生不意味着必须发消息。
- 每个触发实例有独立身份，生成与投递分开。
- 用户取消、专注状态、时段和内容时效，在发送前再次检查。
- 投递结果不明时保留 unknown，不能假装发送成功，也不能盲目重发。
- 重启恢复需要按任务类别决定，不通用地重放一切。

不直接复用 OpenClaw 整个调度服务：其多渠道、权限、宿主状态和 Agent 所有权系统过大。单用户版本用 SQLite 持久任务、短事务认领、版本栅栏和本地 Outbox 实现同样的必要合同。

关心什么、为什么现在关心、哪些主题被拒绝、没有回应是否停止，仍是我们自己的陪伴领域规则。首周即接一个真实通知渠道；单进程先不做worker租约，但仍校验源修订和遗忘代数。

## 7. 桌面陪伴：本轮研究接口，不制作外壳

AIRI 的电源事件适配将休眠、恢复、锁屏和解锁映射为事件，并将监听器清理绑定到所属窗口，值得采用同样的归属原则。[A9]

从 AIRI 和 Open-LLM-VTuber 保留以下概念：在场、忙碌、输入、被打断、播放进度、窗口显示，分别归属不同边界。Pipecat 的轮次控制拥有明确的资源生命周期，测试覆盖策略切换后的处理器清理。[P1–P2]

当前定义`PresenceEvent`、`AttentionState`、`DeliveryReceipt`和`PresentationAction`端口，Trace模拟状态。首周真实投递用浏览器Notification，页面需常驻；离线不尝试，回来只看站内历史，show不证明曝光。暂不做录屏、完整Electron／Tauri窗口或Live2D；若标签常关闭，可单独评估无产品UI的极薄Electron托盘。正式网页、桌面与语音另验。

未来前端只消费已确定的表现指令，不能自行维护人格、记忆和关心计时器。浏览器页面关闭不应改变后台的事实状态。

桌面感知另检查 screenpipe：它把截图和可访问性树配对，区分捕获身份，并对存储阶段的排除状态采用新鲜度检查；信息无法确认时跳过保存。[S1–S2] 当前固定版本采用自定义商业许可，因此只研究机制，不纳入默认代码依赖。[S3]

初期输入事件应保存来源、观测时间、观测范围与有效期；看见过某个页面不能长期当作当前事实。

PygmalionAI 属于最初材料中的角色模型研究方向，本轮不把它作为 Harness 代码底座比较；模型体验需用同一 Harness 做对照，不能通过模型生态名称直接决定运行架构。

这些模拟只能验证 Harness 合同；真实桌面噪音、声音自然度、被打扰感仍必须在后续外壳阶段验证。

## 8. 基于某个项目扩展，还是独立实现

| 路线 | 能省下的部分 | 仍需承担的部分 | 判断 |
|---|---|---|---|
| Fork AIRI 完整应用 | 完整角色、语音和桌面交互 | UI／同步／模型／权限等宿主职责；陪伴事实域与持久关心 | 与当前无前端阶段不匹配 |
| 抽取 AIRI core-agent | 已有端口、队列、取消、协议投影与测试 | 内部依赖拆分、提交合同、状态恢复、记忆与关心领域 | 默认不做；有明确收益才最多2人日验证 |
| 扩展 Letta 本地 Backend | 持久身份、MemFS、模型执行 | 领域状态、投递语义、约定、工具权限与宿主适配 | 当前只阅读借鉴，不做接入 |
| Fork SillyTavern／RisuAI／Agnai | 角色与聊天功能 | 去界面耦合、服务化、调度与持久领域状态 | 不作为本阶段主线 |
| 扩展 OpenClaw | 常驻运行、事件、调度、多渠道 | 缩小通用自主能力、关系记忆与桌面交互 | 更适合后续接入端，当前依赖面过大 |
| 独立小 Harness＋成熟底层库 | 自有领域合同；最少应用级历史包袱 | 自己实现有限状态机、存储映射与验收 | 默认主线；避免自写通用基础设施 |

### 选择翻转条件

默认不是不可改变的结论。只有出现具体复用收益才启用 AIRI 实验，最长两个人日；采用还需同时满足：

1. 核心能在纯 Node 环境运行，不需要 Pinia／DOM／Stage 生命周期。
2. 依赖收敛到可维护的包闭包，保持固定版本及独立构建。
3. 不改上游内部协议就能完成事务提交、取消、部分输出和恢复合同。
4. 相比自有执行器＋模型SDK接入层，明确减少运行逻辑和测试，且不转移授权、预算与提交权力。

满足后可采用AIRI执行辅助适配器，必要时维护小型固定版本抽取包，不Fork全应用，也不绕开自有执行器准入和提交。任意条件不满足就停止适配，回到默认方案。

Letta 此阶段不设实验。未来若明确采用它的记忆工作流，再另行重评，而非为了复用生成循环引入整个宿主。

## 9. 直接复用、借鉴、自建清单

| 分类 | 组件 | 决定 |
|---|---|---|
| 直接复用 | Vercel AI SDK Core及直接DeepSeek Provider | 仅在模型适配器；自有执行器掌握循环，不让SDK自动执行领域副作用 |
| 直接复用 | Zod | 输入、模型结构化结果、领域命令与事件 Schema |
| 直接复用 | SQLite＋better-sqlite3 | 本地事务、任务认领、Outbox、版本和可重建索引 |
| 直接复用 | Fastify、Vitest | 本地 API／SSE 与确定性测试 |
| 备选复用 | Pi AI | 模型网关备选；不同时维护两个默认模型 SDK |
| 条件复用 | AIRI core-agent、Mem0／Hindsight | 通过可替换适配器验证；不先成为事实权威源 |
| 借鉴 | 角色配置、记忆预算、时间／来源、后台归纳、发送栅栏 | 按证据调整为我们的身份与生命周期 |
| 自建 | Persona Policy、相处约定、Memory Commit、Concern Policy | 这是产品领域合同；功能保持小而可测 |
| 自建 | Run／Step、Admission、持久任务、Outbox、公开事件与Trace | 当前只实现单用户有限状态机；保留关系作用域与替换边界 |
| 延后 | 桌面外壳、实时语音、持续感知、多用户／多设备 | 先完成 Harness 验收 |

模型 SDK 比较依据 D1–D3 与 I1–I3。AI SDK 的对象输出适合记忆提取和关心判断；Pi AI 具有明确取消与协议边界，适合作为备选。二者都无法替代我们的事务与关系语义。当前 Pi 包名已变化，实施时依据实际发布版本锁定，不能照旧教程猜包名。

## 10. 本轮尚未证明的事情

- 哪个模型最像目标角色、中文闲聊最自然。
- 哪个记忆引擎在我们的共同经历数据上质量最好。
- AIRI 抽取后的实际依赖体积和维护成本。
- 本地机器上的真实时延、资源占用与长期稳定性。
- 真实桌面通知是否舒服、语音是否有陪伴感。
- 托管网页的多用户隔离、真实负载下的服务容量与DeepSeek额度。

这些不妨碍确定领域合同与默认工程路线，但必须通过后续适配实验、确定性验收和真实使用逐项补证。任何测试目标都不应写成已有测试结果。
