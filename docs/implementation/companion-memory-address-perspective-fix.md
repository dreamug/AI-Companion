## 最终改动

`addressResolution.subject=user` 明确槽位的归属；`replyParticipants` 分开发言助手与接收用户，助手名字来自已发布人格。主生成与评审读取同一份程序投影，用户消息及工具内容不能覆盖它。

事实评审中的待审草稿以真实 `assistant` 消息交付，不再重复塞在 `user` JSON 里；用户原话与助手草稿各自保留说话视角。操作评审继续核对已有状态、实际回执及承诺。

单靠评审提示词仍存在不稳定判断，因此遇到已知名称时，并行执行一次短句解析：只提供实际草稿、名字出现的位置，不提供名字属于谁、期望判定或测试答案。模型标注被命名者及引用方式，程序再按本轮合格档案核对归属；引用、否定、故事对白与同名情况分别处理。该结果可以增加冲突拒绝，不能清除原两项检查的违规。

原两项独立检查及发布屏障保留。命名回合通常为 5 次模型调用，发生完整重写时为 9 次；无相关名称时保持原路径。新增解析与两检查并行、预留额度计入 schema、完整记录调用和费用，取消或任一结果无效均不发布。解析严格验证全部位置，缺失、重复、未知位置不能当作空结果放行。既有 Agent 工具循环预算不变，只为至多两轮解析增加有界调用额度。

主要实现：`src/memory/address.ts`、`naming.ts`、`read-scope.ts`、`reply-contract.ts`、`src/context.ts`、`src/harness.ts`。`web/run-status.js` 增加真实的称呼解析耗时。生产代码无测试昵称、题号或针对原句的条件分支，发布文本不做“我/你”字符串替换。

## 验收口径与结果

复用首次运行前冻结的 24 组题及预期，14 正例、10 反例，没有增加题目来替换失败题，也没有修改预期。覆盖用户称呼、角色自称、双方互称、临时更正与恢复、引用、否定、故事、同名及英文表达。

- 正例要求原两项检查有效且无违规，程序名称核对也无冲突。
- 反例要求原两项检查有效、操作检查无越权，并由事实检查或实际发布屏障中的程序名称核对明确检出 `memory_constraint_conflict`。
- 超时、非法 schema、非法引用以及缺失解析均不算成功拦截。程序拦住模型误放行属于本次修复，未把模型的原错误判定改写成正确。
