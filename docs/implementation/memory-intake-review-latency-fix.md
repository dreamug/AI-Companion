# 关键操作提前接回与检查长尾修正

2026-10-26。已更新主 bot 4317 和交流实验 4341，现有角色、聊天、记忆、设置均保留，未迁移库结构；向量和主动发送维持关闭。4321、4331 未重启。

## 原因与改动

4341 的慢回合首条约 25.9 秒、全条约 27.6 秒。本地记忆读取约 12 ms。后台准入约 1.6 秒已确认需要办理关键操作，但程序在等待旧草稿的事实检查结束后才查看该结果。那组事实检查耗时约 20.2 秒，随后还要提交、重新生成及检查。后续普通回合首条约 3.7 秒，全条约 6.7 秒，其中约 3 秒是发送间隔。

本次不改提取提示、事实判定、操作判定或称呼解析语义，也不扩充昵称或问法词表。只调整以下执行边界：

- 草稿完成时，若同一准入任务已经返回 requires_sync，先提交并重建上下文，不为过时档案启动发布检查。
- 若检查已经启动，准入确认关键操作后会中止该组过时检查；等待两项及适用的称呼解析退出，保留已知费用、将无法得知的用量标记 unknown，再提交及重新生成。不会把取消当作通过。
- 语义操作检查发现的漏意图仍保留原升级路径；三个入口共用同一个升级函数、同一次解析和原有最多一次升级限制。不从助手自己作出的承诺推导写入授权。
- 提交后同时刷新本轮读取授权集合及关键档案。更正/遗忘退出的记录不能留在最终上下文或继续获准展开。
- 发布检查每批默认截止 **8 秒**，包括排队时间。超时中止该批并返回 `memory_review_timeout`，使用既有真实故障回应，不发布未完成检查的草稿、不重试绕过、不自动换模型。仍保留事实检查的 low reasoning 与原 token 上限。该截止不是“整轮必定8秒内成功”的保证；一次允许的修复也仍需完整检查。
- 分条间隔由 1.2至3 秒改为 **0.8至1.5 秒**，按长度计算；首条依然不额外延迟。用户插话、停止和重连的规则不变。

主要实现：`src/harness.ts`、`src/reply-presentation.ts`；`memoryReviewTimeoutMs` 仅为工程配置，默认8秒，不新增用户设置页。

同样复用既有冻结24题及原预期，检查提示和评分口径未改。第一阶段的18万token预留预算不足，只有10题全部完成，另27个组件调用在发送前被本地预算拒绝；这些题原始结果保留为未通过，没有把预算拒绝算成成功拦截。随后将累计预算上限显式扩展到30万，只补这27个未发送的调用，不重跑有效结果。逐个核对 requestHash，补调用与原预算拒绝的请求完全相同。合并有效检查后 **24/24**，没有模型错误重抽或放宽评分。这是组件语义回归，不宣称另做了24轮完整聊天。

这两阶段共用累计台账，保守预算占用 **245,629 token**；取消调用缺少真实用量时按原预留估算，不冒称实际计费已经查清。

浏览器在合成副本使用另一种称呼表达，首条约 **5.99秒**，下一条间隔 **803ms**，真实称呼槽位和回执均提交成功，最终双项检查完成。测试未写入在线用户角色；4332临时服务与标签已关闭。
