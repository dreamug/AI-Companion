## 对照方法

- 模型为现有DeepSeek Flash，使用同一提供方与后台Key。没有改检查提示词、判定、输出上限或重写规则。
- 运行前冻结8组端到端输入，覆盖闲聊、倾听边界、称呼回问、普通偏好、明确保存、更正和无答案；每组各跑串行、并行一次，SP/PS交替，组间不并发，不重跑挑优。
- 每次从同一SQLite备份建立隔离副本，保持相同角色、关系、记忆和近期聊天。语义时钟固定在备份时刻，避免跨交流段或临时称呼到期使配对条件变化；实际延迟用单调时钟测量。
- 串行基线通过仅用于实验的ModelPort包装器，将两项judge的实际提供方RPC串行化；事实检查结束后才发出操作检查。并行组直接同时发出。两组使用同一现行Harness和发布屏障，均保留两项检查。
- 这复现的是旧的检查调用顺序，**没有回滚旧二进制**。两组都沿用现行预算预留及执行逻辑；本次没有网络或预算执行失败，因此未将错误恢复差异当提速收益。
- 另从首个预定串行回合捕获初始草稿及两份检查请求，原样冻结，做4组SP/PS交替的检查对照，排除生成内容变化。日志证明这两份请求的hash在所有复测中分别相同。
- 逐RPC日志验证了28组评审调度：串行无提供方调用重叠，并行有重叠。模型调用层没有插入人工延迟，没有用控时闸门替代真实模型。

8组端到端生成仍可能有模型输出随机差异，网络、提供方队列和缓存也有波动。交替顺序减少了固定先后顺序的影响，不能完全消除这些因素。

## 慢样本与额外发现

b3、b6并行组比串行组慢，均因事实检查对临时称呼给出冲突判断，多走一次重写和双重复核。核对来源时间、当前交流段及槽位规则后，这属于评审误拦截：有效的交流段临时称呼应覆盖长期称呼；评审却将长期值当成更晚且必须优先的值。同请求检查对照的串行组也出现了一次同类误判。

b8两组都经历重写：并行组草稿作了无依据的存储否定，确实需要修正；串行组被同类称呼误判触发重写。称呼误拦截既增加延迟，也可能把正确称呼改错，不能用“Run已完成”掩盖质量问题。

本轮没有为改善成绩改提示词、放宽检查或移除慢样本；这组结果保持原样。称呼优先级在评审投影与判断中的一致性，是后续需要单独修复并验收的问题。

后续更新（2026-10-26）：该误拦截已单独修复并更新 4331，详见[称呼优先级修复与严格复测](companion-memory-address-priority-fix.md)。本页的原始延迟、失败与重写结果保持不变，不把后续修复追溯计入旧对照成绩。
