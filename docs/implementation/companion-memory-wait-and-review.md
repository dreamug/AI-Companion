## 用户看到什么

| 实际阶段                       | 等待超过800ms后的状态        |
| ------------------------------ | ---------------------------- |
| 记忆准入、上下文组装、回复生成 | 小野正在想怎么回应…          |
| 正在调用记忆读取或记忆来源工具 | 小野正在回想相关的事…        |
| 事实与操作检查、回复重写       | 小野正在整理回复…            |
| 真正发布回复                   | 正在回复，分条发布沿用原进度 |

名字取当前角色；不到800ms显示“已收到”，排队时显示“正在等待回复”。超过8秒保留当前阶段并附上“这次有点慢，你可以继续等待或停止”。这些是界面状态，不生成角色聊天气泡，不假装所有延迟都由读取记忆造成。

阶段由后端实际执行点驱动，产生仅含Run ID及阶段枚举的`run.progress`事件，沿现有SSE游标刷新快照。取消、结束和恢复中断时清除活动阶段。没有新增轮询接口或专门的关心Agent。

## 检查并行如何保持原发布条件

1. 一次评审冻结草稿、当前用户投影、读取依据和真实操作回执，两项检查均使用这一个版本。
2. 在同一事务中预留两次调用预算，先校验合并后的调用数及上下文上限，再一起派发；第二次预算不足时第一笔预留也回滚，不只启动一项。
3. 正常的语义拒绝不会取消另一项，完整收齐两项判断，再合并缺陷决定修复或失败。
4. 服务错误、无效JSON或无效引用令整组失败并中止、收尾另一项；不遗留评审、迟到重写或迟到发布。用户取消及硬截止沿同一取消信号传播。
5. 修复后的新草稿仍重新经过两项检查。单项通过不产生发布资格；失败用固定故障回应，Run仍计失败，不拿故障回应算答对。
6. 正常回合仍是准入、生成、事实检查、操作检查共4次模型调用。预算上限、已知用量及未知用量的保守预留继续计数，取消也保留已发生的调用数。没有通过省略检查或减少评分要求提速。

旧版实例仍走原来的顺序检查路径；CM3并行条件由既有`memoryV3`配置限定。

## 耗时记录与查看

Run新增可选`progress`及`timings` JSON字段，无需数据库迁移。计时间隔使用单调时钟，界面阶段时间戳仍使用墙钟。记录排队、准入与提交、记忆读取、上下文组装、生成、事实检查、操作检查、整组评审等待、重写及工具；另记录首稿和回复可发布时间。失败/取消跨度也保留，不填成成功。

每个跨度有开始偏移、持续时间、结果及评审轮次；Run、快照和Trace可以读取。前端“Trace / 维护 → 选择运行 → 查看 Trace 和上下文”先展示可读耗时摘要。旧回合没有记录就明确说明，不倒推或补造历史耗时。

事实检查、操作检查和整组评审等待互相重叠，不能三项相加算总耗时。回复可发布表示服务端已具备发布资格，不等于用户已读；分条节奏另包含在处理总时长中。

## 验证结果与实际限制

- 类型检查、隔离编译通过；最终完整回归46文件、720项通过。本轮新增17项：CM3执行链10项、前端状态与耗时摘要7项。
- 控制两项评审的独立闸门，证明同时启动；一项先通过时正文保持空；两项通过后才发布。正常回合4次用量完整累加。
- 覆盖双项缺陷合并、重写后双重重审、提供方失败、无效JSON/引用、取消、超时、预算预留回滚、阶段实时事件、恢复清理及800ms/8秒边界。超时在CM3明确计失败，仍不发布原草稿。
- 运行前用户自然试聊8轮为4.5至9.3秒，中位数5.735秒。这是历史自然样本，不是配对性能基准。
- 更新后尝试在原演示角色验证，遇到该角色当日100,000 token预算上限；保留该失败及实际用量，没有抬高预算、重置账本或跳过评审。该轮不是成功的提速样本。
- 随后使用独立临时库、脚本模型和人工闸门做真实浏览器控时回归，不调用付费提供方、不复制用户聊天。逐项看到思考、实际读取、生成、检查、8秒提示、单项通过仍等待、双项通过才发布及维护面板耗时摘要。
- 控时回归故意延长各阶段，总耗时约79秒，使用测试专有180秒截止；这些数值不能作为4331延迟或优化幅度。4331原截止未调整。模型调用依然受网络、提供方并发和输出长度影响，目前不宣称端到端P50/P95改善比例。
- 4331用户试聊角色保留原100,000 token日额度，核对时已记录84,394 token；后续还可能受预算限制。没有调整任何角色的额度。
