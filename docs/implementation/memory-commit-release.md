## 问题与改动

原实现把 `unconfirmed_commit` 与明确保存意愿绑定，空白记忆的完整读取回合也可能完全跳过评审。因此普通闲聊和偏好更新可以冒出“我会记住”“旧记录已经作废”“以后一直按新值”等错误承诺。

本次所有开启 `memoryReplyGuard` 的 V2 聊天回合均检查，不用关键词正则猜测有没有承诺，也不依赖是否检索到事实。明确保存意愿只决定是否检查**重复征求**；无依据写入、未来保存承诺与不必要的流程播报适用于普通回合。

程序交付 `memoryOperations`：当前执行范围、长期写入能力仅由界面承担、已完成操作为空、提取登记不等于提交、当前输入不自动改变存储记录、未来召回不受保证。V2 聊天工具只读或登记提取，确实不能确认、更正、作废或删除长期事实；不是凭模型回答伪造空回执。用户文本、粘贴回执与助手旧话都不能授予操作权限。

生成端区分当前采用新值、转述用户未来愿望、存储记录变更。新偏好可用于本次回答，不能由此宣布旧记录已被替换。条件式、能力式的未来新资料保存承诺同样检查，不能擅自把未限定范围的承诺解释成仅本次使用。已有确认事实可以自然回忆；用户/他人保存文件、身体学习、引用或否认承诺不误判成助手写入。

## 已确认状态不是本轮写入回执

第一组新题暴露了证据缺口：评审此前只拿到事实文本，缺少确认状态，于是把“这条已经确认”误当作“我刚替你确认”。

`memoryReplyReadData` 现在另外交付 `confirmedFacts`，包含真实读取记录的 id、修订、文本和确认状态。它只来自程序生成的上下文及真实记忆检索结果；用户粘贴、助手历史、原文展开、待确认记录与日摘要不能授予此状态。

这允许报告记录现有确认状态，仍不允许伪造当前回合新增、修改、删除等操作。记录是否已确认、用户现在实际偏好什么、助手本轮是否执行写入，是三件不同的事。用户明示改变偏好后，旧偏好不用于本次选择，不等于后台旧记录已失效。

## 独立检查与发布边界

合并的长评审提示在增加规则后重新出现读取范围误拦截，因此最终将两项检查分开：

1. `facts`：读取范围与有依据的偏好约束。
2. `operations`：持久化操作、未来记忆承诺、主动办理，以及显式保存时的重复征求。

两项都通过才发布。不同检查不能返回对方负责的违规代码，错范围或格式不合法会失败，不静默清空结论。每项保存原句、作用域、理由与违规代码。预期答案、题目标签及评分标准不进入任一检查。

普通回合为一次生成加两次独立评审。需要修复时最多一次：事实检查通过且违规仅涉及操作/流程时，按语义评审给出的唯一原句位置移除完整句子，再执行两项检查，总共五次调用。使用 `Intl.Segmenter` 划分整句，不按保存词语或主题删字；引句歧义、只有渲染后匹配、移除后为空或存在事实问题，均回到完整重写，再执行两项检查，总共六次调用。沿用原有硬上限、Run 截止与费用计量。没有无限重抽或固定替代答复。第二次仍不合格就不发布；执行过工具的回合仍不自动重放或重试。

此路径用于避免全文重写在保留正确内容时又新增未来承诺；被删内容必须有语义评审证据，剩余内容也必须再次双检。它不能修复事实错误，也不能把空白拒答算成成功。

主动关心是另一条公开出口，也在进入 Outbox 前执行 `operations` 检查，并沿用后续来源、修订、epoch 和准入检查。拒绝后不入队、不重生成、不重放跟进行为。每个后台调用保留独立预算和截止；不改变正式 V1 的行为。
