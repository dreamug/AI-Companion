# 两道漏召回与 25000 条读取延迟修复

> 新增问法的 19/24 后续逐题复核、评分修复及真实回答验证见[五题复核与回答边界](memory-answer-five-case-audit.md)。本文保留当时的字面评分与性能快照。

日期：2026-10-24。承接[完整记忆验收](memory-complete-acceptance.md)。本轮只改代码、测试与隔离评测；未迁移正式库、未修改正式服务开关、未重启正式服务。只读复核的 6 个正式库仍全部为 user_version=1。

## 1 修复与原因

两道原失败题的原文、预期事实和固定 E5 权重保持不变。职业记录原本排在语义候选第 11 位，被最终前五条挤出；称呼记录原本未进入语义前 12。

新增查询侧职业／称呼词汇归一化，保留原问题的主体、否定与时间，在语义查询中补充检索意图，并给关键词后端提供对应别名。这是两类通用意图，不按问题 ID 或完整问题字符串返回答案；不写入新事实、不改证据、不改变确认资格，也无需重建已有 passage 向量。新主题题集在评测前固定，包含其他职业／昵称、家人、过期／失效记录、虚构域和未知属性。

延迟根因包括：查询末尾对全部记录重复哈希、重复关键词检索、超时后重算读取结果、同步读取全部 BLOB、每查询全表扫描置顶／事件，以及对三百个候选逐一重复查询来源。修复为：

- 复用已验证的资格、签名和索引覆盖集合，按 ID 直接定位命中行；关键词候选只取一次。
- 资格快照按事实版本、域、有效时间与来源序号绑定，展示变化重查证据。热态词法查找复用该合格快照，仍按本 Run 截点过滤；扫描不再为每条记录分配临时数组或排序闭包。
- 置顶／事件候选按版本缓存，返回副本；Memory 写入使其失效，事务内不发布缓存，回滚不能污染后续读取。按连接复用带作用域参数的 SELECT 语句，每次仍读取当前行，不缓存行内容来代替资格校验。
- BLOB 按 128 行分页读取、校验并让出执行机会，整块 Float32 矩阵一次转移到扫描 worker；资格构建每 64 条让出一次。
- worker 使用连续矩阵和有界前 12 排序，保持与穷举余弦相同的加法顺序、掩码和相同分数排序。
- 超过 4096 个向量片段的冷快照，前台最多等 25 ms 的快照准备窗口；其余准备继续后台进行，返回 `memory_snapshot_loading` 和有标记的词法结果。准备好后才编码／扫描语义查询。初始化可用性与一次读取的延迟分开报告，不能把降级冒充混合检索成功。
- 已启用向量的隔离实例在空闲索引循环中，同时预热编码模型、已有向量矩阵和资格快照，减少模型就绪后的首次查询等待。只读预热不递增事实或索引版本；正式开关保持关闭。新增大库回归覆盖模型尚未就绪时预备快照、模型就绪后首次读取即命中 hybrid 的路径。

仍保留整体 250 ms 语义截止目标，内部为后处理预留约 30 ms。取消查询释放调用者；遗忘／关闭取消所属服务的全部派生工作，迟到快照不得复活。索引代数变化单独降级，不误报事实快照变化。没有新增正式数据库表或修改模型权重。

## 3 性能门槛与实测

设备为 Apple M1 Max、macOS arm64，E5 使用 CPU。容量数据采用共用合成来源以控制矩阵扫描自变量，为合成短事实、每事实一个 384 维 Float32 向量；矩阵容量试验不作为语义准确率。模型已经就绪时，分别测 50／500／5000／25000 条的首次读取与后续各 100 次读取；25000 条另以全新 SQLite 连接、读取服务和扫描 worker 再做 3 轮，每轮首次读取加 100 次。没有强制清除操作系统页面缓存，不宣称物理磁盘冷启动。

模型自身首次加载单独计时，并在尚未就绪时真实调用读取，验证前台不会等待模型加载。所有原始延迟、模式和降级原因保留，初始化期间的词法结果没有从百分位分母删除。

| 25000 条试验          | 首次读取 ms | 后续 P99 ms | 后续最慢 ms | 超过250 ms／超时降级 |
| --------------------- | ----------: | ----------: | ----------: | -------------------- |
| 原服务冷缓存          |       115.3 |       124.2 |       136.3 | 0／0                 |
| 新连接／新服务第 1 轮 |       111.6 |       155.1 |       155.6 | 0／0                 |
| 新连接／新服务第 2 轮 |       118.9 |       107.8 |       127.9 | 0／0                 |
| 新连接／新服务第 3 轮 |       124.5 |       105.3 |       122.5 | 0／0                 |

4 次冷读范围 **111.6–124.5 ms**；400 次后续查询合并 P50 **49.9 ms**、P95 **89.1 ms**、P99 **127.9 ms**、最慢 **155.6 ms**。全部样本通过 250 ms 门槛，首次进入 hybrid 后没有再次降级。

初始化阶段仍有实际成本：主试验首次 hybrid 出现在约 **2.36 秒**；404 次读取（含4次冷读）中，91 次明确标记快照 loading、313 次实际为 hybrid。它们全部进入延迟统计，不能把91次说成语义命中。模型冷加载约 **4.87 秒**，加载中的前台读取 **5.5 ms** 返回，带 `embedding_not_ready`；并未等待模型加载完成。

实际 E5 编码与后台索引并行的100次查询：P95 **56.8 ms**、P99 **86.0 ms**，无 timeout/busy。50／500／5000 条同样通过门槛。

第一轮强制验收曾捕获两次热态超时，未放行，完整失败结果保留在 `test-results/memory-fix-final-performance/`。进一步减少临时对象与重复 SQL 编译后，重新完整执行本轮4次大库冷启动才通过；未丢弃那两条样本。

强制门槛检查首次读取、全部后续样本均不超过 250 ms、无 timeout/busy，且确实进入 hybrid；首次进入 hybrid 后不得再次退回词法。允许初始化时明确标记 loading。未就绪的编码模型及初次快照准备仍有实际耗时，修复的是前台阻塞和就绪后的尾延迟，不能宣称所有语义资源都在 250 ms 内完成加载。

本机通过不外推低配设备、MPS 或所有文本长度／多片段数量；这些范围保持单独验收。

```sh
npm run verify
npm run test:memory:web
npm run test:web
MEMORY_EVAL_OUT=test-results/memory-fix-recheck npm run test:memory:recall
MEMORY_PERF_OUT=test-results/memory-perf-recheck npm run test:memory:performance
```

后一个命令启用强制性能门槛，只使用临时目录；失败会保留结果并返回非零状态。源码阶段定位可用 `scripts/memory-profile.ts`，其插桩结果仅用于定位，不作为最终延迟成绩。
