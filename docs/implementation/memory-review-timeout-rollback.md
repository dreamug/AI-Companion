# 撤回过紧的发布检查截止

2026-10-26。4341最近两次失败均为 `memory_review_timeout`：主生成约1.3至1.4秒、操作检查约1.0至1.8秒、称呼解析约0.9秒；事实检查被刚加入的8秒截止取消，整轮约9.4秒失败。此前还有一轮事实检查约8.9秒并成功完成，已说明该截止会截断有效结果。

这是上一次修正的取舍错误：把“慢”变成“失败”，没有解决事实检查本身的长尾。

## 已上线的热修复

- 默认单批检查截止 **8→30秒**，原整轮运行上限仍保留；不再在8秒时取消仍在正常执行的检查。
- 事实检查模型、low reasoning、token预算、证据、判定规则及JSON校验不变；事实与操作检查以及适用的称呼解析仍须完成并通过。
- 过时草稿提前取消及关键操作提前接回的修复保留。
- 0.8至1.5秒分条间隔保留。
- 原有两条失败聊天保留，不伪造成功、不自动重发用户消息。

已更新4317和4341；其余实例不变。更新前备份，十个库的schema、messages、memories、sources、runs、settings逻辑指纹更新前后一致。未发送草稿已在页面重连后恢复并核对。没有改正式库结构、人格、记忆内容、向量或主动发送开关。

新增回归以受控时钟证明：事实检查有效结果在8.1秒后返回时，草稿此前保持不可见，系统仍等待结果，最后两项完整检查通过后才发布。显式设置的较短截止、取消及故障回归仍保持原拒绝规则。全量 **52文件、809/809**、类型检查和隔离编译通过。

另外用无用户数据的临时网页注入9.1秒模拟事实检查，验证8秒后不会提前失败。这只证明截止行为，不是实际提供方的速度或准确性成绩；该网页不作为线上bot的模型或回退。

## 速度实验未上线

为判断是否能在保留同样检查内容的情况下提速，运行前冻结了17个语义正反控制（读取不可用、关键词/混合空结果、完整空读取、预算/时间/食材/条件约束及未知职业）和既有24个称呼正反例。未发送真实用户健康对话，只使用合成资料和已存在的冻结题。

对照仍使用Flash、同一完整检查提示、证据和严格解析。候选关闭额外reasoning，使用1500输出上限；没有跳过任何一项检查。结果：

快速候选将符合“不早于10点”限制的10点方案误判为冲突；另有引用/转述称呼的误拦。**候选没有达到门槛，未上线。** 没有为这些题追加特定词、改标签、放宽评分或重抽结果。

代码实际只改默认截止并增加回归，没有加入新的事实检查配置或模型分流系统。检查偶发慢的问题仍存在，不能将这次恢复可用性写成“长尾已根治”或承诺所有回复都很快。进一步提速须独立验证，不能再用短超时包装速度。
